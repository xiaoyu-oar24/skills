# 📚 软件生命周期五维文档布局与演进设计方案

> **核心思想**：文档是知识图谱，不是 Git Commit 历史。文档应随代码演进而演进，而非每次修改都新建文件。通过 **What (需求) → Why (设计) → How to Execute (计划) → Status (跟踪) → How to Use (指南)** 形成完整的软件工程知识闭环。
>
> **定位**：长周期技术架构决策 (ADR / Specs)  
> **版本**：v2.4.1（决策精细化与安全边界补充）

---

## 🎯 一、 背景与演进动机

随着项目协同复杂度的提升，原有的“四象限布局”（`specs/` / `plan/` / `tracking/` / `guide/`）在实际落地中暴露出两个核心痛点：

1. **业务需求（What）无处安放**：缺乏独立的产品需求文档（PRD）存放位置，导致业务规则被强行混入 `specs/`（架构设计）或 `plan/`（实施计划）中，破坏了技术设计文档的纯粹性。
2. **概念修辞语义失真**：在数学与逻辑学中，“象限 (Quadrant)”严格指由直角坐标划分的 4 个区域。当扩展为 5 个目录时，称“五象限”名不副实，缺乏工程严肃性。

因此，提出**“软件生命周期五维文档布局 (5-Dimensional Docs Layout)”**优化演进方案，在完善知识链路的同时，引入弹性按需扩展机制，防止形式主义与过度设计。

---

## 📐 二、 五维矩阵定位与完备性分析

基于软件工程生命周期（ALM）与 MECE 原则（相互独立，完全穷尽），划分以下五个维度：

| 维度象限 | 目录路径 | 核心定位 | 解决的核心问题 | 存续生命周期 | 必选 / 可选 | 实施状态 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **需求文档** | `docs/reqs/` | 产品需求描述 (PRD)、页面交互、业务规则 | **What** (要做什么) | **中长周期** — 验收后冻结保留作为业务资产 | 按需判定（业务功能必选，纯技术重构可选） | ✅ v2.4.0 已落地 |
| **设计规范** | `docs/specs/` | 技术架构决策 (ADR)、接口设计、数据模型 | **Why** (为什么这么做) | **长周期** — 随代码演进的“活文档” | **核心必选** | ✅ v2.4.0 已落地 |
| **执行计划** | `docs/plan/` | 实施计划、任务拆解与技术落地路线 | **How to Execute** (准备怎么做) | **短周期** — Feature 交付后移入 `docs/.archive/plan/` | **核心必选** | ✅ v2.4.0 已落地 |
| **进度跟踪** | `docs/tracking/` | 执行过程 Checklist、多 Agent 协作状态 | **Execution Status** (做到了哪一步) | **超短周期** — 验收后移入 `.archive/tracking/` 或删除 | xy-feat 内必选；单线程任务可选 | ✅ v2.4.0 已落地 |
| **使用指南** | `docs/guide/` | 面向开发者与使用者的 How-to 手册 | **How to Use** (别人/未来怎么用) | **长周期** — 随功能迭代持续维护 | **核心必选** | ✅ v2.4.0 已落地 |
| **统一归档** | `docs/.archive/` | 历史旧版、已完成计划、废弃文档 | - | 永久存续 | - | ✅ v2.4.0 已落地 |

## 💡 三、 判定决策树与作用域安全边界 (KISS / YAGNI 原则)

为了消除 AI 在“按需”判定上的模糊性，防止“该建不建”或“不该建乱建”，特制定精准的**判定决策树**与 **`xy-feat` 作用域保护规则**。

```
docs/
├── INDEX.md               # 知识索引导航 (必选)
├── reqs/                  # [按需 - 决策树判定] 业务需求文档 (PRD)
├── specs/                 # [核心 - 必选] 技术架构设计 (ADR)
├── plan/                  # [核心 - 必选] 实施计划与任务拆解
├── tracking/              # [xy-feat必选 / 独立单任务按需] 进度清单
└── guide/                 # [核心 - 必选] 面向开发者的使用指南
```

### 1. `reqs/` 判定决策树
AI 助手在决定是否创建独立 `docs/reqs/<功能名>-req.md` 时，必须严格按以下顺序判定：

```
是否创建 reqs/？
├─ 用户明确要求编写/整理需求文档？ ───► ✅ 创建独立 reqs/
├─ 属于纯技术重构/性能优化/API对齐？ ───► ❌ 跳过 reqs/，内联至 specs/
├─ 包含新页面、新业务交互或变更有感UI？ ──► ✅ 创建独立 reqs/
└─ 其他无法裁决场景 ───────────────► 提问向用户确认
```

### 2. `tracking/` 判定决策树与 `xy-feat` 作用域保护
为保护 `xy-feat` 工作流阶段 3 多 Agent 并发写入安全（避免高频写入 `plan.md` 引起冲突），对 `tracking/` 实行**分级作用域保护**：

```
是否创建 tracking/？
├─ 上下文为 /xy-feat 工作流调起的任务？ ──► ✅ 强制创建（防多 Agent 并发写入冲突）
├─ 使用了 dispatching-parallel-agents？ ──► ✅ 强制创建
├─ 单线程任务且卡片/步骤 ≤ 3 个？ ──────► ❌ 跳过 tracking/，内联至 plan.md 尾部
└─ 其他单任务场景 ──────────────────► 默认创建（宁可多建，不漏追踪）
```

## 📝 四、 内联降级与标准化模板

当按决策树判定跳过 `reqs/` 或 `tracking/` 时，必须使用以下标准 Markdown 模板进行内联降级，保证 AI 解析的一致性。

### 1. `reqs/` 内联降级模板 (在 `specs/<功能名>-design.md` 头部)

```markdown
# [功能名] 技术架构与设计规范

> **降级说明**：本任务属于纯技术改造/优化，无独立业务 PRD。需求背景已内联在本文档中。

## 1. 需求背景与改造目标
- **当前痛点**：[简述现有架构/代码痛点]
- **改造目标**：[简述改造后达成的技术指标/收益]
- **非目标 (Non-Goals)**：[明确本次不做的范围]
```

### 2. `tracking/` 内联降级模板 (在 `plan/<功能名>-plan.md` 尾部)

```markdown
---

## 📋 实施进度 Checklist (内联 Tracking)

> **降级说明**：本任务为单线程轻量任务，进度追踪已内联在 plan 中，不单独生成 tracking.md。

- [ ] **阶段 1：准备与重构**
  - [ ] 任务 1.1: [具体子任务描述] `file_path:line`
  - [ ] 任务 1.2: [具体子任务描述]
- [ ] **阶段 2：核心逻辑实现**
  - [ ] 任务 2.1: [具体子任务描述]
- [ ] **阶段 3：验证与交付**
  - [ ] 任务 3.1: 运行单元测试 / 验证点
```

## 🔄 五、 活文档与归档管理规范

### 1. 领域主体命名法 (Domain-Driven Naming)
* **严格禁止日期前缀**：拒绝 `2026-07-24-gateway-design.md`，统一采用领域主体命名 `gateway-proxy-design.md`。
* **前缀一致性**：同一功能模块在不同维度共享相同的 `<功能名>` 前缀（如 `file-upload-req.md`、`file-upload-design.md`、`file-upload-plan.md`）。

### 2. 原地更新与统一归档
* 同一功能的文档在演进中**优先原地更新**（活文档理念）。
* 旧版或已被替代的文档，统一追加 `-archived` 后缀并移入顶层归档目录 `docs/.archive/{象限}/`（例如 `docs/.archive/specs/gateway-proxy-design-archived.md`），废弃分散在象限内部的 `.archive/` 子目录方案。

## 🗺️ 六、 知识导航索引闭环

任何文档的增加、重命名、归档或删除，必须同步更新 `docs/INDEX.md`。`INDEX.md` 作为人类开发者与 AI Agent 检索项目知识的统一入口，必须保持 100% 的准确度。
