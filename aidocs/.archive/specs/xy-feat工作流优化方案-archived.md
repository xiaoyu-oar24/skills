## 一、 优化背景与现状分析

`xy-feat` 作为端到端功能开发的主编排技能，通过引入 superpowers 优先与 `references/` 降级双模机制，成功将正文压缩至 113 行，实现了高可维护性与渐进式披露。

然而，在针对真实复杂项目（如多包工程、样式微调、多子代理并发开发）的实践中，发现该工作流在阶段衔接、资源开销、并发安全与死锁逃生机制上仍存在 **6 个切中痛点的优化空间**。

---

## 二、 6 大核心优化项与落地方案

### 1. 阶段顺序调整：消除“先归档、后审查”的文件路径失效错位

- **问题根因**：
  - 当前阶段 5 触发 `docs-layout-quadrant`，会将 `docs/plan/<功能名>-plan.md` 标记为 `[DONE]`，并把 `docs/tracking/<功能名>.md` 移动至 `docs/tracking/.archive/` 目录。
  - 随后进入阶段 6（代码审查），其流程说明（`fallback-verify-finish.md` 第 55 行）强制要求 CR 子代理读取原始的 `plan.md` 与 `tracking.md` 路径作为评审依据。
  - 这导致 CR 子代理因文件已移入 `.archive/` 而读取失败或报 FileNotFound 错误。
- **落地方案**：
  - 将**代码审查与收尾**前置，将**使用指南产出与全量归档**后置。
  - 修正后流转顺序：`阶段 4 验证完成` → `阶段 5 代码审查与收尾` → `阶段 6 指南产出与全量文档归档`。

---

### 2. 避免重复全量运行测试：基于状态差分的测试去重

- **问题根因**：
  - 阶段 4 刚刚通过 `self-check-trinity` 完成了全量测试。
  - 若阶段 5 (CR) 未提出修改意见，代码没有任何变动，阶段 6.2 在收尾时仍会强制通过 Bash 重新跑一次全量测试（`fallback-verify-finish.md` 第 69 行）。
  - 在大型单体或多包项目中，重复测试会浪费 1~3 分钟的计算时间与 Token。
- **落地方案**：
  - 在阶段 6 收尾测试前增加 Git Diff 检测：若 `git diff HEAD_SHA` 为空（即阶段 4 之后源码无改动），则跳过重复的全量测试，仅输出“代码无变更，沿用阶段 4 校验凭证”。

---

### 3. 非单测场景下的 TDD 逃生通道：校验驱动开发 (VDD)

- **问题根因**：
  - 阶段 3 护栏规定 `NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`（无失败测试不写实现）。
  - **现实死锁**：在纯 CSS/UI 页面调整、Dockerfile 配置修改、或缺少单元测试框架的 Legacy 项目中，AI 无法编写可运行的失败单元测试，导致流程死锁或逼迫 AI 伪造单测。
- **落地方案**：
  - 增加 **TDD 适用性判定与校验驱动开发（VDD, Validation-Driven Development）** 逃生机制：
    ```
    前置判断：当前任务是否属于纯 UI/样式、配置修改或无单测框架环境？
    - 否 → 严格执行 TDD（RED → GREEN → REFACTOR）
    - 是 → 自动切换为 VDD：
      1. RED 阶段：运行静态检查（如 tsc / dockerfilelint / stylelint）或打印当前页面未修饰状态断言，确认有待改进项。
      2. GREEN 阶段：写入最小修改，运行静态检查通过。
    ```

---

### 4. 消除并发覆写冲突：子代理状态汇报收束

- **问题根因**：
  - 阶段 3 在处理独立任务时，允许通过 `dispatching-parallel-agents` 派发多个子代理并行开发。
  - 但 `fallback-tdd.md` 要求每个子代理完成后直接编辑 `docs/tracking/<功能名>.md` 标记 `✅`。
  - 多个并行子代理同时编辑同一个 Markdown 文件，会导致竞态覆写（Race Condition），后完成的子代理会冲掉先完成子代理的修改。
- **落地方案**：
  - **规则禁令**：并行子代理禁止直接用 `Edit` 修改全局 `docs/tracking/<功能名>.md`。
  - **状态收束**：子代理只需在其最终返回消息中包含 `Task N Complete`，由**主调度代理**在接收完并行子代理结果后，集中更新跟踪文件。

---

### 5. 高频弹窗解绑：Git 写操作的阶段性批量预授权

- **问题根因**：
  - 护栏 4 规定 `git add / git commit` 等写操作必须获得用户明确授权。
  - 在 TDD 流程中，每个 Task 都有原子提交点。若有 10 个 Task，AI 会连续弹窗询问 10 次授权，打断开发体验。
- **落地方案**：
  - 在阶段 2 规划文档送审时，在提问中加入批量授权声明：
    > “*批准本执行计划即视为授权 AI 在阶段 3 TDD 执行过程中，针对上述任务卡片自动执行本地 Git 原子提交 (`git commit -m ...`)*。”
  - 将单次频繁打断降级为阶段性一次授权。

---

### 6. 减少对话往返：阶段 1 方案设计的“一站式 Draft 呈现”

- **问题根因**：
  - `fallback-init-design.md` 第 51 行要求：“每呈现一个分节（架构、数据流、错误处理）后询问用户确认”。
  - 连续打断 4~5 次会导致沟通体验碎片化。
- **落地方案**：
  - 改为“一站式 Draft 呈现 + 分节标记”，仅在遇到**重大底座选型冲突**（如 2~3 种方案选型分歧）时提问，其余情况下直接展示完整的结构化设计 Draft 供用户统一审批。

## 三、 优化项实施计划与收益汇总

| 序号 | 优化主题 | 核心改进措施 | 预期收益 |
| :---: | :--- | :--- | :--- |
| **1** | **阶段顺序** | 调整顺序为：验证 → 审查收尾 → 指南与归档 | 消除 CR 子代理找不到已归档文件的报错 |
| **2** | **测试去重** | 源码无变动时跳过阶段 6 重复全量测试 | 节约 1~3 分钟执行时间与 Token |
| **3** | **TDD 逃生** | 样式/配置改动自动切换为 VDD（校验驱动） | 解决非单测场景下的流程死锁 |
| **4** | **并发安全** | 并行子代理禁止直接写 `tracking.md`，由主代理收束 | 彻底消除多子代理并发写文件的竞态冲突 |
| **5** | **授权优化** | 阶段 2 审批时合并预授权阶段 3 原子提交 | 减少 80% 的高频确认打断 |
| **6** | **方案呈现** | 阶段 1 由多轮打断改为 Draft 结构化一次性呈现 | 提升沟通效率，减少对话轮次 |
