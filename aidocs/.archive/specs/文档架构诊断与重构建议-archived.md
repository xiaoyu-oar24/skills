# Docs 文档架构诊断与重构建议

> ✅ **状态：已全部实施**（2026-07-22）。本文的建议（去日期前缀、四象限生命周期管理、知识索引）已落实，保留本文作为设计决策记录 (ADR)。

  遵守项目强制的 specs / plan / tracking / guide 四象限是对的，但目前的落地方式存在严重的反模式（Anti-pattern），极其不利于 AI 的检索（RAG）。

  致命问题：时间戳命名法（Write-Only Graveyard）

  - 现象：2026-07-15-网关代理转发.md。
  - 批评：这是最典型的“流水账式”文档组织。**文档是知识图谱，不是 Git Commit 历史！**带有日期的前缀会让文档变成一旦写完就再也不维护的“一次性产物”。当 AI
  搜索“网关如何工作”时，它无法确定 2026-07-15 的文档是否就是最终的、最新的系统状态。

  Docs 架构演进方案（遵循四象限框架）

  1. 废除日期前缀，转向“领域主体”命名 (KISS 原则)
  - 文档命名必须仅描述模块/领域。
  - Before: docs/specs/2026-07-15-网关代理转发-design.md
  - After: docs/specs/gateway-proxy-design.md 或 docs/specs/网关代理转发.md
  - 让文档随着代码的演进而演进，而不是每次修改都在新日期下建立新文件。

  2. 象限生命周期管理 (YAGNI 原则)
  不同象限的文档具有完全不同的生命周期，AI 必须明确它们的过期边界：
  - plan/ (实施计划)：短周期。这是开发前的 Draft，Feature 交付后，Plan 应当废弃或标记为 [DONE]，AI 不应再将其作为系统现状的参考源。
  - tracking/ (执行追踪)：超短周期。这是任务拆分的 Checklists。强烈建议：合并到 Pull Request 描述或外部 Issue 跟踪系统中。如果一定要放在 Git 中，任务验收后必须归档（放入
  .archive/）或删除。代码库不该存储执行状态。
  - specs/ (设计规范/架构决策 ADR)：长周期。这是系统的宪法。这里应该记录“为什么这么做”（Why），要求高度结构化。AI 应当将此视为核心约束。
  - guide/ (使用指南/最佳实践)：长周期。这是面向开发者的 How-to。

  3. 建立知识索引 (Context Root)
  当前目录散落了十几个文件，AI 缺乏入口。
  - 建议：在 docs/ 根目录维护一个 INDEX.md 或在 README.md 中建立领域知识树。说明“网关功能”对应的 spec、guide 分别在哪个文件。利用 Markdown 链接 [[关联文档]] 形成一张扁平导航网。

  总结行动点

  如果确认进行架构升级，作为架构师我首推以下两步：
  1. 执行批量重命名：去除所有 docs/ 下的时间戳前缀，按业务模块合并重名或重叠的文档。
  2. 清理过期的 Tracking：将历史进度文档清理出当前工作上下文，防止污染 AI 之后的决策路径。
