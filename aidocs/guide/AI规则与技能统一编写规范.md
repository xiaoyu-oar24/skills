# AI 规则与技能统一编写规范

本文档定义 AI 规则（Rule）与技能（Skill）的统一编写标准，覆盖从命名、结构、章节编写到发布维护的完整生命周期。面向两类读者：

- **技能/规则作者** — 如何设计并编写一份高质量的 `SKILL.md` 或 `RULE.md`
- **项目维护者** — 如何在多工具环境中配置、挂载和管理规则/技能

> **版本说明（2026-07-22）**：本版在原有内部约定基础上，对齐了市面通用的 Agent Skills 标准（Anthropic 官方技能编写最佳实践、开放 Agent Skills 规范），新增正文规模红线、渐进式披露拆分模式、评估驱动开发与技能组合纪律等内容。

---

## 1. 概念与命名规范

### 1.1 规则 vs 技能

| 维度 | 规则 (Rule) | 技能 (Skill) |
|:---|:---|:---|
| **定义** | 对 AI 行为的长期约束与编码规范 | 可复用的多步骤功能工作流 |
| **粒度** | 项目级 / 文件级 | 跨项目公用 |
| **存放** | 项目根目录（`CLAUDE.md`、`.cursor/rules/`） | 技能容器目录（`skills/<name>/SKILL.md`） |
| **激活** | 会话初始化时自动加载，或基于 `globs` 按文件类型注入 | 用户显式调用（`/<name>`）或语义匹配触发 |
| **典型例子** | "所有 API 返回值必须用统一响应格式包装" | "端到端功能开发工作流：需求→设计→TDD→验证→审查" |

两者在**文件格式和编写模式上完全统一**（Markdown + YAML Frontmatter + 标准章节），区别仅在于存放位置和激活方式。

> **决策指南**：如果一段 AI 指令描述的是"每次做 X 类操作时都要遵守的约束"→ 规则；如果它描述的是"完成一个完整功能的多步骤流程"→ 技能。如果判断不了，先做成规则——规则的激活成本更低，从规则升级为技能比反过来容易。

### 1.2 命名规范

技能和规则目录**统一使用 `kebab-case`**（小写字母 + 连字符），与 npm 包名、GitHub 仓库名惯例一致：

| ✅ 正确 | ❌ 错误 | 原因 |
|:---|:---|:---|
| `xy-feat` | `xy:feat` | 冒号在 macOS/Windows 文件系统中有特殊语义，且 cc-switch 等工具不兼容 |
| `health-probe-discipline` | `HealthProbeDiscipline` | 跨平台大小写敏感性不一致 |
| `api-name-drift-defense` | `api_name_drift_defense` | 下划线在 URL/Markdown 链接中易被吞掉 |
| `z-paging-best-practices` | `z-paging` | 过于简短，不足以描述技能职责 |

**硬性约束**（对齐开放 Agent Skills 规范）：

- `name` 长度 **≤ 64 字符**，仅允许小写字母、数字、连字符
- 不得包含 `anthropic`、`claude` 等保留词
- 推荐**动作导向**命名（动名词/动宾结构，如 `processing-pdfs`），避免无意义缩写和个人前缀

**命名自检**：一个陌生人只看目录名，能否大致猜到技能做什么？不能 → 名字不够描述性。已存在的历史命名如需保留（维护者既定决策），必须在 `description` 中充分补偿可发现性，并在审计记录中注明。

### 1.3 生命周期管理

每个技能/规则应明确其当前阶段，推荐在 `description` 或正文首段中标注：

```
阶段          标记方式                        行为预期
─────         ──────                          ──────
开发中        description 中注明 "WIP"        可频繁修改，不稳定
稳定          version >= 1.0.0                修改需考虑兼容性
废弃          description 前缀 "[DEPRECATED]"  触发时提示用户迁移方案
归档          目录移至 .archived/              不再激活
```

- **废弃时**：在 `description` 最前面加 `[DEPRECATED]` 标记，并说明替代方案（如 `"使用 xy-feat 替代"`）。保留 1-2 个版本周期后再归档
- **破坏性变更**：修改已稳定技能的 `name` 或核心工作流时，需同步更新所有引用该技能的 `CLAUDE.md` Hook 和文档索引
- **版本号语义**：修复示例错误/措辞 → patch；新增章节/护栏/参考文件 → minor；改名/工作流重构 → major

## 2. 文件结构与 Frontmatter

### 2.1 目录结构

```
skills/<skill-name>/
├── SKILL.md              # 核心工作流（必需）
└── references/           # 参考材料（可选，按需加载）
    ├── code-templates.md #   代码模板、配置片段等支撑材料
    ├── fallback-*.md     #   拆分出去的分支/降级流程细节
    └── evals.md          #   触发评测集（见 §4.5）
```

- **`SKILL.md`** — 技能的核心工作流、触发条件、护栏，**必须存在**。调度逻辑、阶段划分、出入口条件与安全护栏必须在正文中自足；AI 只读正文也能知道"做什么、按什么顺序、什么不能做"
- **`references/`** — 可选的按需加载文件，服务于两类用途（均对齐"渐进式披露"原则）：
  1. **支撑材料**：代码模板、配置片段等被 `SKILL.md` 引用的内容（如 `uniapp-wechat-scaffold` 的脚手架模板）。此类技能正文的流程逻辑必须自足，但生成物的具体内容来自 references
  2. **流程细节外置**：当正文超过规模红线（见 §2.1.1）时，将分支流程、降级流程、详细模板拆到 references，正文保留调度骨架与"何时读取哪个文件"的指引（如 `xy-feat` 的 `fallback-*.md`）

> 正文引用 references 文件时，必须写清**相对路径**和**读取时机**（"执行阶段 X 前读取"），禁止出现"详见某文件"但 AI 不知道何时该读的情况。

### 2.1.1 正文规模红线与渐进式披露

技能采用三级加载模型：**元数据（name + description，常驻）→ 正文（触发时加载）→ references（执行中按需加载）**。未触发的技能几乎零成本，被触发的技能其正文会全额注入上下文，因此：

- **正文（SKILL.md 除去 frontmatter）不得超过 500 行**，建议控制在 5000 tokens 以内
- 超过红线时**必须拆分**：把细节移入 references，正文只保留调度逻辑、阶段出入口与安全护栏
- 拆分后正文仍须满足 §2.1 的"调度自足"要求——禁止把护栏、触发条件也外置
- 内容在正文与 references 之间**单一来源**：同一流程不得在两处各写一份（双源维护必然腐化，见 §5.8）

### 2.2 基础格式

所有规则和技能文件采用 **Markdown + YAML Frontmatter**。即使工具不解析 YAML，也能作为纯文本理解：

```markdown
---
name: "skill-or-rule-name"
description: "动作导向的描述。TRIGGER when: 触发条件。SKIP: 跳过条件。"
globs: "*.{ts,tsx,vue}"
version: "1.0.0"
---

# 技能/规则名称

正文内容...
```

### 2.3 Frontmatter 字段

| 字段 | 必需 | 说明 |
|:---|:---|:---|
| `name` | **必需** | 唯一标识，≤ 64 字符，kebab-case。**opencode 硬校验：缺失则技能被系统忽略** |
| `description` | **必需** | 意图路由核心依据，**≤ 1024 字符**。详细写法见 §2.4。**警告：缺失时技能虽能加载但不会出现在技能索引中** |
| `globs` | 可选 | 文件匹配模式，基于当前文件类型静默激活（Cursor/Windsurf 支持） |
| `version` | 可选 | 语义化版本号 |
| `author` | 可选 | 署名 |

> ⚠️ **description 缺失警告**：当技能加载器检测到 `description` 字段为空或不存在时，会输出 `warning: skill "xxx" has no description: — it will load but won't appear in the skills index`。这表示技能仍可被显式调用，但**不会出现在技能索引列表中**，AI 无法通过语义匹配自动触发该技能。

### 2.4 description 编写准则

`description` 是 AI 路由分发的最关键字段，需同时回答两个问题：**做什么（WHAT）+ 何时用（WHEN）**。本仓库采用中文 TRIGGER/SKIP 写法（与英文第三人称 "Use when... / Do not use for..." 语义等价，主流工具均可识别）：

```
一句话功能概括 + TRIGGER when: <激活条件> + SKIP: <跳过条件>
```

**TRIGGER/SKIP 约定**（非正式 DSL，但各主流工具按关键词匹配）：

- `TRIGGER when:` 后跟激活条件，多条件用 "或" 连接（语义 OR），用 "且" 表示 AND
- `SKIP:` 后跟跳过条件，用于抑制误触发。误触发成本高的技能（如端到端工作流），应把 SKIP 写得比 TRIGGER 更严格，甚至限定"仅显式 `/name` 调用时触发"
- 关键词建议使用中文以匹配用户自然语言输入
- 大小写不敏感（工具匹配时通常会 normalize）

**YAML 格式兼容性要求**（重要）：

`description` 值**必须用双引号包裹**，且内部避免使用可能破坏 YAML 解析的特殊字符：

| 避免使用 | 推荐替代 | 原因 |
|:---|:---|:---|
| 花括号 `{}` | 用文字描述，如 `code-message-data` | YAML 中 `{` 表示内联映射，可能导致解析歧义 |
| 箭头符号 `→` | 用逗号或顿号分隔 | 部分严格解析器可能视为非法字符 |
| 未转义的冒号 `:` | 用"如"、"包括"等词汇替代列表中的冒号 | 冒号在 YAML 中是键值分隔符 |
| 嵌套引号 | 去掉嵌套引号或用斜体/书名号替代 | 避免与外层引号冲突 |

| 示范 | 内容 |
|:---|:---|
| **优秀** | `"Vue3 迁移工具。TRIGGER when: 用户提到重构、迁移、Vue3升级。SKIP: 文件已包含 script setup 或项目非 Vue 技术栈。"` |
| **错误** | `Vue3 迁移工具。TRIGGER when: 用户提到"重构"` （未加引号 + 嵌套引号，YAML 解析失败） |
| **错误** | `"返回 { code, message, data } 格式"` （花括号在部分解析器中会被识别为映射） |

## 3. 正文章节编写指南

一份规范的技能/规则文件，正文应包含以下五大章节。章节标题推荐使用 emoji + 中英双语，降低不同 AI 模型的解析歧义。

### 3.1 🎯 触发条件 (Trigger Conditions)

明确 AI 在何种场景下激活：

- **意图触发** — 用户说了什么关键词（在 `description` 的 `TRIGGER when:` 中声明）
- **文件特征触发** — 当前操作的文件匹配了什么模式（通过 `globs` 字段）
- **复合触发** — 两者同时满足才激活（高精度场景）
- **抑制条件** — 什么情况下即使匹配了也不触发（在 `description` 的 `SKIP:` 中声明，正文建议同步重述）

```markdown
## 🎯 触发条件
- 用户提到 "重构"、"迁移"、"升级到 Vue3" → 激活
- 当前文件匹配 `*.vue` 且包含 `export default { … }` (Options API) → 激活
- 文件已包含 `<script setup>` → 跳过
```

**技能间冲突豁免**：若本技能与另一技能的规则存在重叠场景（如探针端点是否套统一响应格式），必须在 SKIP 或正文显式声明谁豁免、谁优先（见 §4.6）。

### 3.2 ⚙️ 依赖与先决条件 (Prerequisites)

列出执行前必须满足的条件——越具体越好，避免 AI 在缺环境时产生幻觉：

```markdown
## ⚙️ 依赖与先决条件
- Node.js >= 18，包管理器为 pnpm
- 项目根目录存在 `tsconfig.json`
- ESLint 已配置且可通过 `npx eslint --version` 验证
- 运行环境假设为类 Unix 终端（示例命令使用 ls/grep/cat）；Windows 请改用等价命令
- （可选）Vitest 已安装，用于验证阶段运行测试
```

**编写原则**：
- 每个条件都附带验证命令，AI 可以先检查再执行而非假设一切就绪
- **声明平台假设**：示例命令基于特定终端（Unix / Windows）时必须明说，避免 AI 在异构环境照搬失败
- **避免钉死版本**：依赖第三方库时写 `v2.8+` 并注明"执行前先确认项目实际版本"，而非写死小版本号（时效性信息会静默过期，见 §5.10）

### 3.3 📖 标准工作流 (Core Workflow)

强制 AI 按阶段执行，每个阶段的输出是下一阶段的输入：

```markdown
## 📖 标准工作流

### 阶段 1：理解
- 读取 `<待修改的文件路径>`，理解现有实现
- 若参数不明确，通过 AskUserQuestion 向用户确认，**禁止猜测后直接执行**

### 阶段 2：设计
- 基于读取结果给出修改方案（不写代码，先描述思路）
- 方案获用户确认后进入下一阶段

### 阶段 3：执行
- 使用 Edit 工具逐文件精确修改，**禁止整文件重写**
- 每个文件修改后确认无语法错误

### 阶段 4：验证
- 进行类型检查（TypeScript 项目执行 `npx tsc --noEmit` 或等价检查）
- 自动识别项目包管理器（根据 `pnpm-lock.yaml` / `yarn.lock` / `package-lock.json`），执行对应的测试命令，例如 `pnpm test -- --run <test-file>`
- 任一验证失败 → 回到阶段 3 修复，**禁止跳过验证直接结束**
```

**编写原则**：
- 每个阶段指定应调用的**具体工具**（如 `Read`、`Edit`、`Bash`），不要写"读取文件"而写"使用 Read 工具读取"
- 面向多工具环境的技能，允许使用泛化工具名（"命令行/终端、编辑文件、文件搜索"）以保持跨工具兼容，但同一技能内必须统一风格
- 阶段之间的传递条件要明确（"方案获用户确认后" 而非 "然后"）
- 验证步骤必须是**可自动化的命令**，不要写"人工检查"

### 3.4 ⛔ 行为护栏 (Guardrails)

列出 AI **绝对不能做**的操作。护栏是防御性的——宁可多写，不可遗漏：

```markdown
## ⛔ 行为护栏
- 禁止修改 `node_modules/`、`.git/`、`.env` 等敏感文件和目录
- 测试未通过，禁止执行 `git commit` 或 `git push`
- 删除文件或覆写已有配置前，必须先列出清单并向用户确认
- 禁止使用 `rm -rf`、`git reset --hard` 等不可逆命令
- 发现文件存在内容冲突时，中断流程并通知用户，**禁止自动合并**
```

**编写原则**：
- 每条护栏对应一个**具体的破坏场景**（"如果 AI 做了 X，会导致 Y 灾难"）
- 护栏不超过 8 条——超过后 AI 注意力衰减，后半段形同虚设。如果确实需要 8+ 条，把最致命的 5 条放最前面
- 避免抽象表述（"注意安全"），每条必须是可机械判断的动作（"禁止执行 `git push`"）
- **破坏性操作确认闸**：工作流涉及删除、批量移动/重命名、覆写已存在文件时，护栏中**必须**有一条要求"先列出清单并获得用户确认"——删除文件无 Git 兜底场景尤其如此

### 3.5 📝 模板与范例 (Few-Shot Examples)

提供 `<Bad>` / `<Good>` 对比代码块。这是纠正 AI 行为最有效的手段——比十段文字描述更精准：

````markdown
## 📝 模板与范例

### <Bad> — 禁止模式
```typescript
// 回调嵌套，严禁使用
api.getUser(id, function(user) {
  api.getProfile(user.profileId, function(profile) {
    // ...
  });
});
```

### <Good> — 推荐模式
```typescript
// 强制使用 async/await + 错误处理
try {
  const user = await api.getUser(id);
  const profile = await api.getProfile(user.profileId);
} catch (error) {
  logger.error("Fetch failed", error);
  throw error;
}
```
````

**编写原则**：
- `<Bad>` 和 `<Good>` 必须成对出现，单独一个 `<Good>` 没有对比效果
- 每对范例覆盖一个具体场景（不要一个 `<Good>` 试图展示所有最佳实践）
- 优先覆盖**最常见的犯错场景**而非边缘 case
- **示例必须可运行**：范例中的 import、变量、命令必须完整自洽（AI 会原样照抄）。发布前自问：这段代码贴进对应环境能不能直接跑？`import` 缺符号、未定义的变量、自相矛盾的命令行参数都是事故（见 §5.11）

对于**工作流或行为交互型技能（Workflow Skills）**，Few-shot 范例应侧重对比 **AI 的交互与工具调用模式**：

### <Bad> — 盲目覆写行为
```markdown
# 行为反模式：跳过方案设计与沟通，直接通过 Write/Edit 整文件覆写。
- 步骤：AI 直接调用 Write 写入新文件，擦除了不相干的原有辅助函数，中途出错中断。
```

### <Good> — 渐进式与防御性编辑行为
```markdown
# 行为推荐：设计先行，精确编辑，并前置状态校验。
- 步骤：
  1. 调用 Read 读取目标模块。
  2. 提出精确修改方案送用户确认。
  3. 调用 Edit 仅针对目标行微调，不破坏周围代码。
  4. 根据锁文件识别包管理器，运行对应的测试命令验证。
```

## 4. 进阶编写技巧

### 4.1 意图与特征双重触发

不要仅依赖用户说关键词。结合 `globs` 字段实现文件特征触发：

```yaml
# 仅在用户操作 src/api/ 下的文件，且提到 "接口" "API" "请求" 时激活
globs: "src/api/*.ts"
description: "API 接口规范。TRIGGER when: 用户操作 src/api/ 下的文件或提到'接口''请求封装'。"
```

### 4.2 CLI 状态校验

工作流中要求 AI 使用**安全的只读命令**获取真实状态，避免基于过期上下文产生幻觉：

```markdown
1. **强制读取**：给出建议前，先执行 `npx tsc --noEmit` 获取当前类型错误
2. **解析结果**：分析输出，定位所有类型冲突
3. **反馈用户**：将问题列表展示给用户，确认后再修改
```

关键原则：
- 只允许**无副作用**的查询命令（`--noEmit`、`--dry-run`、`status`）
- 修改性命令（`install`、`build`、`deploy`）需用户确认
- 不假设工具已安装：先 `which <cmd>` 或 `npx <cmd> --version` 检查

### 4.3 Good/Bad 对比的三层递进

1. **语法/风格层** — 用什么语法模式（async/await vs 回调）
2. **架构/设计层** — 用什么结构组织代码（依赖注入 vs 硬编码）
3. **错误处理层** — 完整的边界条件覆盖（try/catch + 日志 + 用户提示）

三层都覆盖的范例比只展示语法层的范例有效 3 倍以上。

### 4.4 渐进式披露拆分模式

当技能逼近 500 行红线时，按以下模式拆分（本仓库 `xy-feat` 为参考实现）：

```
SKILL.md（≤ 300 行，调度骨架）
  ├─ 触发条件、依赖表、命名规范、各阶段出入口、护栏、范例   ← 常驻正文
  └─ 各阶段只写："优先调用 X 技能；降级读取 references/fallback-x.md"

references/
  ├─ fallback-<阶段>.md   ← 完整内联流程，仅在该阶段且降级时才读取
  └─ evals.md             ← 触发评测集（见 §4.5）
```

要点：
- 正文必须保留"何时读哪个文件"的明确指引（依赖表中给出阶段 ↔ 文件的映射）
- 安全相关内容（护栏、确认闸、Iron Law）**不外置**，必须常驻正文
- references 文件头部注明"本文件仅在 … 时按需读取"，避免 AI 全文预载

### 4.5 评估驱动开发（Trigger Evals）

description 是路由依据，但"写得像能触发"不等于"真的会触发"。每个技能应在 `references/evals.md` 维护**触发评测集**：

```markdown
# <skill-name> 触发评测集

## 应触发（Expected：激活）
1. "用户提示词 A"
2. "用户提示词 B"
3. "用户提示词 C"

## 不应触发（Expected：跳过）
1. "易混淆提示词 X"
2. "易混淆提示词 Y"
```

要求：
- **至少 3 条应触发 + 2 条不应触发**；"不应触发"用例覆盖最相似的误触发场景（相邻技能、自然语言 vs 显式调用、豁免领域）
- 每次修改 `description` 或触发条件后，逐条回归验证
- 刻意收窄触发的技能（如仅显式 `/name` 激活），"不应触发"用例与"应触发"同等重要

### 4.6 技能组合纪律

所有已安装技能共存于同一元数据空间，彼此是"邻居"而非孤岛：

- **禁止规则矛盾**：两个技能不得对同一场景给出相反指令。存在重叠领域时（如探针端点 vs 统一响应格式），必须在一方的 SKIP/护栏中显式声明豁免与优先级
- **调用环必须有界**：技能 A 调用技能 B、B 又调回 A 时，必须在一方显式声明终止条件（如"回归验证仅执行一轮，不再级联"），禁止依赖隐式重试上限兜底
- **跨技能复用要降级**：调用其他技能时提供"技能不可用"的内联降级路径（如 `unified-api-response` 对 `self-check-trinity` 的调用），避免硬依赖
- **引用用 name 不用路径**：正文中引用其他技能用其 `name`（反引号包裹），不要写死对方文件路径

## 5. 常见反模式

以下是编写技能/规则时最高频的错误。

### 5.1 把历史叙事当规范写

```
❌ "2026-05-08 timelineAt 功能上线，涉及 5 个模块的重构，详见 docs/ARCHITECTURE.md §5.4"
✅ "时间线功能的数据查询统一走 TimelineRepository，禁止直接在 Controller 中拼接 SQL"
```

规则/技能是**行为约束**，不是**变更日志**。历史事实放进规则文件只会让真正的约束被叙事淹没。

### 5.2 护栏膨胀

```
❌ 25 条护栏，从 "禁止使用 var" 到 "禁止在周五下午部署"
✅ 前 5 条覆盖最致命场景，后面概不赘述
```

护栏超过 8 条后，AI 的注意力集中在前 3-5 条，后半段形同虚设。把非致命的约束移到工作流的"验证阶段"中作为检查点。

### 5.3 description 像产品简介

```
❌ "这是一款强大的 Vue3 迁移工具，支持多种转换模式，性能优异"
✅ "Vue3 迁移工具。TRIGGER when: 用户提到'重构''迁移'。SKIP: 文件已包含 <script setup>。"
```

`description` 的唯一职责是**路由分发**，不是推销。每个多余的字都在稀释触发精度。

### 5.4 硬编码项目特定路径

```
❌ "读取 ~/Documents/my-project/src/config.ts 获取数据库配置"
✅ "读取项目根目录下的数据源配置文件（如 src/config.ts、prisma/schema.prisma）"
```

技能应该是**跨项目可复用的**。涉及项目特定路径时，用参数化表述并要求在"依赖与先决条件"中声明。

### 5.5 工作流只写"做什么"不写"用什么工具"

```
❌ "读取配置文件，分析现有代码结构"
✅ "使用 Read 工具读取 tsconfig.json 和 package.json，确认项目技术栈"
```

现代 AI Agent 可以调用具体工具（Read / Edit / Bash / Grep）。不指定工具，AI 可能选择低效或错误的方式来完成任务。（多工具兼容场景可按 §3.3 使用统一风格的泛化工具名。）

### 5.6 验证步骤不可执行

```
❌ "确认一切正常"
✅ "自动判定项目所用包管理器，执行对应的测试指令：如 pnpm test -- --run <test-file> 确认全部测试通过"
```

验证步骤必须是**可直接复制到终端运行的命令**，"确认一切正常"不是验证，是祈祷。

### 5.7 硬编码特定包管理器命令

```
❌ "使用 yarn install 安装依赖，再使用 npm run build"
✅ "先通过项目根目录下的锁文件探测对应的包管理器（如 pnpm-lock.yaml / package-lock.json / yarn.lock），随后使用探测到的包管理器执行相应命令。如未检测到，提示用户确认。"
```

技能应保持技术栈与包管理器的中立性，由 AI 在运行时动态探测。

### 5.8 正文膨胀与双源维护

```
❌ SKILL.md 写到 600 行，其中 300 行是对外部技能的"内联降级复制"
✅ 正文 ≤ 500 行只做调度；降级流程拆到 references/fallback-*.md 按需读取
```

正文每多一行，触发时的上下文成本就高一分；同一流程在正文和外部技能各存一份副本，上游升级后副本必然腐化。拆分模式见 §4.4。

### 5.9 技能间规则矛盾

```
❌ 技能 A 要求"所有 JSON API 必须套统一格式"，技能 B 的范例让探针端点返回裸 JSON，双方互不提及
✅ 在其中一方的 SKIP 中声明："探针端点豁免统一封装，以 health-probe-discipline 为准"
```

AI 同时装着两个技能，矛盾规则会让行为不可预测。重叠领域必须显式裁定（见 §4.6）。

### 5.10 钉死版本号等时效性信息

```
❌ "本指南基于 z-paging v2.8.6"（组件升级后技能静默过期）
✅ "本指南基于 z-paging v2.8+（执行前先确认项目实际版本，API 以实际版本为准）"
```

版本号、日期、"目前最新"等表述都会过期。必须提及时，附带"先验证再执行"的指令。

### 5.11 示例代码不可运行

```
❌ from fastapi import APIRouter, Request   # 下文却用了未导入的 Response
❌ curl -I -X GET http://localhost/health    # -I 隐含 HEAD，与 -X GET 自相矛盾
✅ 发布前逐段自查：import 齐全、变量已定义、命令参数自洽，贴进对应环境能直接跑
```

AI 会原样照抄范例。示例里的每一个符号都是承诺。

## 6. 发布与维护

### 6.1 存放策略

所有 AI 规则文件应存放在代码仓库中跟随 Git 版本管理。不同工具对项目级规则的读取路径：

| 目标 AI 工具 | 推荐存放位置 | 触发机制 |
|:---|:---|:---|
| **Claude Code** | `CLAUDE.md`（项目根目录） | 会话初始化时自动读取 |
| **opencode** | `~/.config/opencode/skills/skills/<name>/SKILL.md` | 内置技能系统自动加载 |
| **Cursor** | `.cursor/rules/<rule-name>.mdc` | 根据 `globs` 按文件类型注入 |
| **Windsurf** | `.windsurfrules` | 全局注入 |
| **Copilot** | `.github/copilot-instructions.md` | Chat 和代码生成时附加 |

> **多工具混用**：建议建立 `.ai/rules/` 统一目录存放所有规则，各工具入口文件只写一行引导语：*"请在执行任务前，查阅 `.ai/rules/` 下的对应规范。"*

### 6.2 跨工具 Hook 挂载

让一份 `SKILL.md` 同时服务于多工具，需在各工具的配置文件中埋入 Hook：

| 工具 | 挂载方式 |
|:---|:---|
| **opencode** | 自动读取技能目录，无需手动挂载 |
| **Claude Code** | 在 `CLAUDE.md` 中写入：*"若用户指令匹配 `/<skill-name>`，通过 Read 工具读取对应 `SKILL.md` 并遵循其工作流。"* |
| **Cursor / Windsurf** | 将 Hook 写入 `.cursorrules` / `.windsurfrules`，写法同上 |

### 6.3 缓存与生效机制

- 修改规则/技能文件后，**正在运行的会话不会自动感知变更**
- **opencode**：必须重启编辑器或新建会话
- **Claude Code**：重启 Claude Code 客户端会话（退出当前命令行并重新输入 `claude` 启动）
- **Cursor**：重新加载窗口（`Cmd+Shift+P` → `Reload Window`）

> ⚠️ 修改技能文件后，请重启对应工具以确保新配置生效。

### 6.4 快速检查清单

发布前逐项确认：

**元数据**
- [ ] 目录名使用 `kebab-case`，≤ 64 字符，足够描述性，无保留词
- [ ] Frontmatter 包含 `name` 和 `description`（缺失 `name` = 系统忽略；缺失 `description` = 不出现在技能索引）
- [ ] `description` ≤ 1024 字符，同时回答 WHAT + WHEN，包含 `TRIGGER when:` 和 `SKIP:` 语义
- [ ] `description` 值**用双引号包裹**，内部无花括号、未转义冒号、嵌套引号等 YAML 危险字符

**结构与规模**
- [ ] 正文 ≤ 500 行（建议 ≤ 5000 tokens）；超出部分已按 §4.4 拆入 references 且单一来源
- [ ] 正文调度自足：触发条件、阶段出入口、护栏常驻正文；references 引用写明相对路径与读取时机
- [ ] 🎯 触发条件 — 列出意图触发、文件特征触发和抑制条件；与相邻技能的重叠场景已声明豁免
- [ ] ⚙️ 依赖与先决条件 — 每个条件附带验证命令；已声明平台假设；版本依赖写成 `vX.Y+` 而非钉死
- [ ] 📖 标准工作流 — 分阶段、指定工具、阶段间有明确传递条件
- [ ] ⛔ 行为护栏 — 不超过 8 条，按致命程度排序，每条可机械判断；涉及删除/批量移动/覆写的技能含"先确认"护栏
- [ ] 📝 模板与范例 — `<Bad>` / `<Good>` 成对出现；示例 import 齐全、变量已定义、命令可直接运行

**组合与评测**
- [ ] 与已安装技能无规则矛盾；跨技能调用有降级路径；调用环有显式终止条件
- [ ] `references/evals.md` 含 ≥3 条应触发 + ≥2 条不应触发用例，且本次修改后已回归验证

**其他**
- [ ] 无项目特定硬编码路径（或已在依赖中声明）
- [ ] 无历史叙事（变更日志归 git log）
- [ ] 跨工具 Hook 已配置（如项目使用多工具）
- [ ] 生命周期阶段已标注（WIP / 稳定 / 废弃），版本号按 §1.3 语义递增
