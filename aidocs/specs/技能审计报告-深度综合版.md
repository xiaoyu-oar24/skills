## 三、🔴 P1 — xy-feat 工作流逻辑与流程优化（核心关注）

> 以下问题中，P1-1 至 P1-6 已在 `docs/specs/xy-feat工作流优化方案.md`（2026-07-23）中详细论证，但**截至本报告审计时（2026-07-23），当前 `SKILL.md` v4.3.0 中均未实施**。P1-7 至 P1-11 为本轮独立复核新增发现。

### P1-1 阶段顺序缺陷：先归档、后审查导致文件路径失效 ⚠️ 逻辑死锁

- **当前流程**：阶段 5（`docs-layout-quadrant` 执行文档合规整理）→ 阶段 6（代码审查）
- **问题**：阶段 5 会将 `docs/plan/<功能名>-plan.md` 标记 `[DONE]`，将 `docs/tracking/<功能名>.md` 移入 `.archive/`。阶段 6 的 CR 子代理（`fallback-verify-finish.md:55`）需要读取原始 `plan.md` 和 `tracking.md` 作为评审依据，此时文件已被归档，导致 **FileNotFound** 错误。
- **影响**：真实的端到端流程会在评审阶段报错中断，需要人工介入恢复。
- **建议**：交换阶段 5 和阶段 6——`验证 → 审查收尾 → 指南产出与归档`

### P1-2 TDD Iron Law 无逃生通道 ⚠️ 流程死锁

- **当前约束**：`NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`
- **问题场景**：
  - 纯 CSS/UI 调整：无法编写可运行的失败单元测试
  - 配置文件修改（Dockerfile、CI 脚本）：无测试框架可运行
  - Legacy 项目：未配置单元测试框架
- **后果**：AI 在这些场景下面临二选一：①伪造无意义的单测（技术债），②流程卡死无法继续
- **建议**：在阶段 3 前增加 **TDD 适用性判定**，非单测场景自动切换为 **VDD（Validation-Driven Development）**——用静态检查（`tsc`、`stylelint`、`dockerfilelint` 等）替代单元测试作为 RED 阶段

### P1-3 阶段 6 重复全量测试浪费资源

- **问题**：阶段 4 刚通过 `self-check-trinity` 全量测试。若阶段 5-6 期间代码无任何变更，阶段 6.2 仍强制重跑全量测试（`fallback-verify-finish.md:69`）
- **影响**：大型项目中每次浪费 1-3 分钟计算时间与 Token
- **建议**：在阶段 6 测试前增加 Git Diff 检测：若 `git diff BASE_SHA..HEAD_SHA` 自阶段 4 后无变更，则跳过重复测试，直接引用阶段 4 校验结果

### P1-4 并行子代理的 tracking.md 竞态条件

- **问题**：阶段 3 允许多个子代理并行执行独立任务。`fallback-tdd.md:84` 要求每个子代理完成后编辑 `docs/tracking/<功能名>.md` 标记 `✅`
- **风险**：多个并行子代理同时写入同一个 Markdown 文件，后完成者覆盖先完成者的修改（Race Condition）
- **建议**：并行子代理禁止直接写 tracking.md。改为子代理在返回消息中声明 `Task N Complete`，由**主编排代理**在收齐所有并行结果后集中更新 tracking.md

### P1-5 Git 授权逐次打断体验

- **当前行为**：护栏 4 规定 `git commit` 等写操作需逐次授权。TDD 流程中每个 Task 都有原子提交，10 个 Task = 10 次弹窗
- **建议**：在阶段 2 方案审批时合并预授权——"批准本计划即授权阶段 3 中的本地原子提交 (`git commit -m ...`)"

### P1-6 阶段 1 方案设计的碎片化打断

- **当前行为**：`fallback-init-design.md:51` 要求"每节呈现后询问用户确认"，连续打断 4-5 次
- **建议**：改为一次性 Draft 呈现，仅在重大底座选型冲突（2-3 种方案分歧）时提问

### P1-7 阶段 1 `brainstorming` 优先级标注仍存语义矛盾

- 当前依赖表（`:31`）将 `brainstorming` 标注为"**强制**"，虽在表头加了说明（"强制指该阶段不可跳过"），但表的列标题是"优先级"，读者仍可能误解为"外部技能强制依赖"。此外，引导语 `:27` 说"优先尝试技能调用，返回不可用即自动降级"——"强制"与"自动降级"语义互斥。

### P1-8 xy-feat 护栏数量触及 8 条上限且存在工作流规则混入

- 规范 §3.4 明确"护栏不超过 8 条"，§5.2 警告"超过 8 条后 AI 注意力集中在前 3-5 条"
- 当前 8 条护栏中，"上下文对齐"、"调试纪律"、"测试铁律"本质是**工作流规则**而非行为禁令，弱化了真正致命约束（禁止日期前缀、Git 授权、证据优先）的注意力权重
- 历史审计（v2 报告 3.2）已识别此问题并建议精简为 4+1，当前版本实际未按建议执行

### P1-9 `📐 文档命名规范` 为五段式外的非标准章节

- 该章节插入在 ⚙️ 与 📖 之间，规范 §3 定义的标准章节为 🎯→⚙️→📖→⛔→📝 五个
- 历史审计 3.6 已识别，建议"不强制删除但加标注"。当前版本既未合并到 ⚙️ 也未标注"扩展"
- 该内容实质是 `docs-layout-quadrant` 的摘要复述，存在双源维护风险

### P1-10 `description` 字段 401 字符，超出推荐的可维护范围

- 历史审计 4.5 已识别（当时 322 字符），当前增至 401 字符，是其他技能均值的约 1.3 倍
- 建议使用 YAML 多行块标量 `>` 改写以提升可读性

### P1-11 `fallback-init-design.md` 提问策略与 SKILL.md 正文不一致

- `fallback-init-design.md:35` 要求"每次只问一个问题（多选优先于开放式）"
- 但 `SKILL.md:81` 阶段 0 仅写"若用户输入为空或不清晰，向用户提问：'你要做什么功能？'"
- 两处对提问策略的描述粒度不一致，AI 在降级模式下可能按 fallback 的多轮提问、非降级时按正文的单轮处理，行为不可预测

## 四、🟡 P2 — 值得关注的问题

### P2-1 `docs-layout-quadrant` description 521 字符

规范建议 ≤ 1024 字符（硬上限），但该技能的 description 为全部 8 个技能中最长（521 字符），约 2 倍于均值。功能上合法，维护性偏弱。

### P2-2 `z-paging-best-practices` 存在非标准额外章节

`## 📌 核心概念`（`:31-35`）和 `## 常见问题排查`（`:231-250`）独立于五段式结构之外。FAQ 部分有独立价值，但更宜作为 📖 的附录或 `references/` 独立文件。当前混杂在正文中增加了上下文负担。

### P2-3 各技能 `evals.md` 高度模板化

全部 8 个 `evals.md` 均恰好 15 行，结构完全一致（`# <name> 触发评测集` → `## 应触发` 3 条 → `## 不应触发` 2-3 条）。虽然满足规范 §4.5 的最低要求（3 应 + 2 不应），但：
- 用例质量参差不齐——部分"不应触发"条目过于宽泛（如 `"非 uni-app 项目"` 难度过低）
- 缺少对抗性评测（易混淆的边界场景、相邻技能的语义重叠用例）

### P2-4 `unified-api-response` 的 `<Bad>` 示例中 Java 部分存在潜在误导

```java
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
```

这个 `<Bad>` 示例展示了"裸返回对象"的错误模式，但返回类型 `User` 本身是正确的 Java 语法——AI 可能只看到 `@GetMapping` + `@PathVariable` 的模式而忽略"裸返回"的问题本质。建议在 `<Bad>` 的注释中更明确标注"直接返回裸对象、无统一封装"。

### P2-5 `health-probe-discipline` 阶段 4 验证缺失 POST 拒绝测试

验证步骤（`:56-58`）仅覆盖 GET 200 和 HEAD 正常响应两项。护栏要求"显式声明只接受 GET 和 HEAD"，但未验证拒绝行为：`curl -X POST http://localhost:PORT/api/health` → 应返回 405。历史审计 4.2 已识别，但当前版本仍未追加 POST 拒绝验证。

### P2-6 `docs-layout-quadrant` 护栏 7 条中"保留 Git 历史"与其他条目风格不一致

7 条护栏中 6 条是"禁止"/"必须"格式的行为约束，"保留 Git 历史"却是描述性语句（`:125`），风格不统一。
