# 文档产出分级判定（Doc-Tier Gate）架构决策记录

> **状态**：已实施（docs-layout-quadrant v3.2.0 / xy-feat v5.5.0 / lean-docs v1.2.1）
> **决策日期**：2026-08-21
> **关联技能**：`docs-layout-quadrant`（前置闸门定义）、`xy-feat`（阶段 0 档位判定）、`lean-docs`（版本对齐）
> **关联文档**：`../guide/AI规则与技能统一编写规范.md`、`../.archive/specs/xy-feat工作流优化方案-archived.md`（其优化建议已全部落地 v5.0–v5.5）

## 1. 背景与问题

### 1.1 现状

五维象限规范要求任何功能开发都产出五维文档（reqs / specs / plan / tracking / guide）。其中 `plan/`（任务拆解）与 `tracking/`（进度清单）被定义为"核心必选"，`xy-feat` 工作流中 `tracking/` 甚至强制创建。

### 1.2 问题

在真实开发实践中发现：

1. **token 消耗巨大**：小任务（单文件 Bug 修复、配置微调）也被迫产出 4~5 份文档，其中 plan/tracking 在交付后立即归档或删除，属于一次性消耗。
2. **资产价值不均衡**：实践表明，真正有长期价值的只有两类文档——
   - `specs/`（**契约防腐**）：架构决策、接口契约、数据模型，防止代码演进中的契约漂移；
   - `guide/`（**团队资产**）：How-to 操作手册，让后续开发者/团队快速上手。
   - 而 `plan/` + `tracking/` 只是**开发脚手架**：短生命周期，交付即归档，Git 历史已足够追溯执行过程。
3. **缺乏前置判定**：所有任务无论规模，一律走同一套全文档流程，缺少"先判断该不该触发全文档流程"的闸门。

## 2. 决策

引入**文档产出分级判定（Doc-Tier Gate）**：在任何"产出新文档"类调用开始前，先按任务特征判定档位，再按档位决定产出哪些象限。

### 2.1 三档模型

| 档位 | 名称 | 适用场景 | 文档产出 |
| :--- | :--- | :--- | :--- |
| **L0** | 轻量（零文档） | Bug 修复、单文件小改动、配置/样式微调、≤3 步无设计决策 | 不建任何象限文件；决策内联 commit/注释 |
| **L1** | 精简（核心资产） | 常规单模块功能、有设计沉淀价值 | `specs/`（必产）+ `guide/`（按需）；`plan/`、`tracking/` 对话内维护不落盘 |
| **L2** | 全量（五维全出） | 跨模块/跨包、多 Agent 并行、重大架构决策、新页面新交互、用户明确要求 | 五维全出 |

### 2.2 Agent-Friendly 补强

自 docs-layout-quadrant v3.2.0 与 xy-feat v5.5.0 起：

1. 新建功能文档必须携带最小机器可读头：`status`、`tier`、`domain`、`updated_at`，有来源时加 `source_workflow`。
2. L1 档不落盘 plan/tracking，但阶段出口与任务状态必须写入 specs 的 `## Execution State` 节，保证跨会话恢复。
3. L2 档归档时同步 frontmatter 为 `archived`；交付验证通过后先标记 `delivered`。
4. `INDEX.md` 必须校验相对链接有效，并覆盖五个象限的全部非归档功能文档。

### 2.2 判定决策树

```
文档档位判定（在产出任何文档前执行）：
├─ 用户明确要求完整五维文档/全流程？ ────► L2 全量
├─ 是否全部命中以下轻量特征？
│   ├─ Bug 修复 / 配置调整 / 纯样式微调 / 文档修正
│   ├─ 改动 ≤ 3 个文件（或单模块局部）
│   ├─ 无新接口契约 / 无新数据模型 / 无架构决策
│   └─ 无新页面 / 无新交互
│   └─ 全部命中 ──► L0 轻量
├─ 是否命中任一全量特征？
│   ├─ 跨模块 / 跨包边界
│   ├─ 多 Agent 并行开发
│   ├─ 新的架构决策 / 接口契约 / 数据模型
│   ├─ 新页面 / 新交互 / 变更有感 UI
│   ├─ 需要正式 plan 供多会话执行
│   └─ 用户明确要求完整文档
│   └─ 任一命中 ──► L2 全量
└─ 其余常规功能 ──► L1 精简
```

### 2.3 关键规则变化

- **废弃"核心三支撑"**：`specs/`+`plan/`+`guide/` 必选 → 改为"核心资产 `specs/`+`guide/` + 脚手架 `plan/`+`tracking/` 按档落盘"。
- **tracking/ 决策树调整**：移除"/xy-feat 上下文强制创建"条款（改由档位判定决定），保留**多 Agent 并行强制创建**以保障并发安全（子代理禁写、主编排代理集中更新）。
- **guide/ 按需**：新组件/新 API/新工作流等有团队使用价值时写；纯内部重构无对外价值时跳过，禁止空壳文档。

## 3. 方案对比

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| **A. 三档分级判定（采纳）** | 区分度最好；L0 零文档、L1 只留核心资产、L2 全量；token 节省最明显 | 判定本身有少量认知成本（可观察谓词明确，成本低） | ✅ 采纳 |
| B. 两档（轻量/全量） | 改动最小 | 常规功能仍被迫全量，节省有限 | ❌ 区分度不足 |
| C. 维持现状（全部五维） | 规则简单 | 小任务 token 浪费严重 | ❌ 问题未解决 |

## 4. 实施要点

1. **判定先行**：`docs-layout-quadrant` 新增"前置闸门"章节，所有产出新文档的调用必须先判定；`xy-feat` 阶段 0 接入判定，判定结论需向用户说明。
2. **L1 档 plan/tracking 不落盘**：任务拆解与进度在对话内维护，交付后无需归档，消除归档成本。
3. **空壳文档禁令**：任何档位禁止生成空白占位文件；被跳过的象限内容按需内联（reqs 内联至 specs 头部、tracking 内联至 plan 尾部或对话）。
4. **多 Agent 并发保护**：L2 档使用多 Agent 并行时，tracking/ 强制创建并保持"子代理禁写、主编排代理集中更新"约束不变。

## 5. 预期收益

- **token 消耗**：L0/L1 档任务文档产出量下降 60%~100%（视任务类型），长期积累收益显著。
- **知识质量**：`specs/` + `guide/` 作为核心资产被更聚焦地维护，信噪比提升。
- **规则一致性**：docs-layout-quadrant / xy-feat / lean-docs 三技能对齐同一分级模型，消除"双权威"漂移。

## 6. 回滚与兼容

- 本决策为增量演进：L2 档行为与旧版"五维全出"完全一致，仅 L0/L1 新增降级路径，不破坏既有文档结构。
- 若分级判定导致误判（如 L0 档漏掉了本应沉淀的契约），可随时通过用户要求或档位复核升级档位，文档可补产。
