# Vue3 B端业务组件审计规范

## 🎯 触发条件
- **激活**：用户明确指定**组件路径**（文件或目录），并请求"审计 / 审查 / review"该组件
- **硬性前置**：路径是执行的必要条件。未提供路径时**必须**先询问用户，用户拒绝提供 → **不执行**，禁止自行猜测或搜索组件路径
- **抑制（SKIP）**：
  - 未指定组件路径（无论是否提到审计关键词）
  - 指定路径但非 Vue3 或非 Element Plus 二次封装组件
  - 全仓范围审计 → 交由 `ponytail-audit`
  - 提交/合并前的代码审查收尾 → 交由 `requesting-code-review`

## ⚙️ 依赖与先决条件
- 目标组件为 Vue3 Composition API + `<script setup lang="ts">`
- 目标组件基于 Element Plus 二次封装（本技能审计的核心对象）
- 组件路径由用户显式提供（相对或绝对路径均可）；执行前使用文件系统工具确认路径存在且指向 `.vue` 或组件目录
- 本技能不依赖 globs / 目录扫描自动发现组件

## 📖 标准工作流
### 阶段 1：路径确认
- 若用户未提供路径，通过提问向用户确认，禁止猜测
- 用户拒绝或无法提供路径 → 立即终止，不执行审计

### 阶段 2：读取组件
- 使用 Read 工具读取目标组件文件（含 `<script setup>`、模板、样式）
- 如组件引用了内部子组件/类型，按需读取关联文件以理解完整实现

### 阶段 3：按清单评分
- 严格按下方"审计检查清单"逐项核对
- 每个维度内逐项打分（完全满足 2.5 / 部分满足 1 / 不满足 0），维度得分 = 各项之和（满分 10）
- 加权总分 = Σ(维度得分 × 权重)，满分 10 分
- 任一检查项不适用时记 2.5 分并在报告中注明"不适用"

### 阶段 4：输出报告
- 严格按"输出格式"结构输出，问题必须带行号

## 审计检查清单

### 1. EP 集成 [权重:30%]
- [ ] `v-bind="$attrs"` 是否透传
- [ ] Props 类型是否 extends Element Plus 原始类型
- [ ] Slots 是否完整透传（含具名插槽）
- [ ] Events 是否无冲突透传

### 2. TypeScript 类型 [权重:25%]
- [ ] 禁止 any，使用泛型或具体类型
- [ ] Emits 有完整类型定义
- [ ] Expose 类型对调用方友好
- [ ] 联合类型表达运行时约束（如 mode='edit' 时 onSubmit 必填）

### 3. AI 友好性 [权重:25%]
- [ ] JSDoc 描述"意图"而非"事实"
- [ ] 命名语义化，可预测与 EP 的关系
- [ ] 至少有 2 个不同场景的使用示例
- [ ] 导出路径明确，无 barrel file 歧义

### 4. 业务抽象 [权重:20%]
- [ ] 封装有增量价值（非简单 wrapper）
- [ ] 配置项 ≤ 15 个（经验阈值），超过则建议拆分
- [ ] 默认值符合 B 端常见需求
- [ ] 业务逻辑与 UI 解耦

## 输出格式
严格按以下结构输出：
1. 📊 评分表（4 维度 × 10 分制，含各维度得分、权重、加权总分，总分满分 10 分）
2. 🔍 问题清单（行号 + 严重度 + 修改建议 + AI 影响）
3. 🤖 AI 友好性专项分析
4. ✅ Top5 优先改进项（按 ROI 排序，ROI = 影响面 × 修复成本倒数，需简述理由）

## ⛔ 行为护栏
- **路径缺失即不执行**：未提供组件路径时，禁止通过目录扫描、搜索、猜测组件位置的方式自行执行
- **只读审计**：本技能只产出报告，禁止直接修改组件代码；修改建议一律写入报告，是否实施由用户决定
- **范围锁定**：审计范围仅限用户指定的组件，禁止擅自扩大到未指定的目录或文件
- **禁止破坏性操作**：不删除、不重命名、不覆写任何文件
- **冲突即上报**：路径指向非 Vue 组件、非 EP 封装组件或路径不存在时，停止并反馈用户，禁止强行套用检查清单

> **违反护栏的字面规定，就是违反护栏的精神。** 任何"只是扫一眼目录""顺便改个小 bug"的想法都从护栏的精神上被禁止，没有例外。

## 🚩 红牌自查（出现任意一条即停止）

审计过程中如果出现以下任何一种念头或行为，**立即停下**，回到"向用户要路径 / 只读输出"的正确轨道：

- 我准备用文件搜索/目录扫描来定位组件
- 我觉得"路径很明显，不用问用户"
- 用户给了目录路径，我准备自己猜具体是哪个文件
- 我准备在审计报告中顺手修改组件代码
- 我准备把审计范围扩展到用户没指定的其他组件

**出现任意一条 → 停止，向用户确认路径或范围，恢复只读。**

## 辩解与真相（Rationalization Table）

> **实测记录（2026-08 压力测试，3 场景 3/3 零违规）**：无路径强制 / 模糊路径暗示 / 顺手改码诱惑 全部守住护栏。下表辩解均为**预防性**——它们是用户最可能用来施压的话术，即使实测未触发，也要在更强压力下继续顶住：

| AI 的辩解（或用户施压话术） | 真相 |
|:---|:---|
| "用户说'那个组件'，我扫一眼目录就能猜到" | 猜错对象 = 审错组件，整份报告作废；目录扫描被护栏明文禁止 |
| "目录里就一个文件 / 路径很明显，不用问" | "明显"是你的假设，不是用户的事实；目录下可能有未提及的子目录或未提交文件 |
| "用户暗示'你应该能找到'就是授权" | 暗示 ≠ 路径；用户可能记错目录、文件已改名或移动 |
| "反正只读，顺手改个小 bug 也没关系" | 审计与修复职责分离；一旦改动，用户就失去了对原状的真实审计基线 |
| "全仓/相关组件一起审了更高效" | 范围锁定是护栏，擅自扩大 = 审计了用户没要求的东西 |
| "用户是主管又在赶时间，他说'顺手修了'就是授权" | 权威和截止时间不是授权；越权改码仍会破坏审计基线，报告照写、修复另走流程 |

## 📝 模板与范例

### <Bad> — 无路径自行搜索（禁止）
```markdown
用户: "帮我审查一下这个组件"
AI: "好的，我先搜索 src/components 下的 .vue 文件……（自行扫描目录并猜测目标组件）"
```
**问题**：违反"路径必须显式提供"；扫描全目录既慢又可能审错对象。

### <Good> — 路径确认后执行
```markdown
用户: "帮我审查一下这个组件"
AI: "请提供要审计的组件路径（文件或目录）。"
用户: "src/components/BizForm.vue"
AI: （确认路径存在 → 读取组件 → 按 4 维度清单评分 → 输出报告）
```

### <Bad> — 评分体系混乱（禁止）
```markdown
"EP 集成：8 分"  ← 未说明 8 分怎么来的，且与其他维度无权重关系，总分无法核算
```

### <Good> — 评分可复现
```markdown
"EP 集成 [权重 30%]：10/10（4 项全满足）
 TypeScript 类型 [权重 25%]：7.5/10（发现 1 处 any）
 加权总分 = 10×0.30 + 7.5×0.25 + … = 8.4/10"
```
