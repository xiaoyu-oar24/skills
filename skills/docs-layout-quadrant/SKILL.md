# docs-layout-quadrant

> **核心思想**：文档是知识图谱，不是 Git Commit 历史。文档应随代码演进而演进，而非每次修改都新建文件。需求文档（What）→ 设计文档（Why）→ 执行计划 → 进度跟踪 → 使用指南，形成完整的软件工程知识链路。
> **分级思想**：文档资产有层级——`specs/`（契约防腐）与 `guide/`（团队资产）是长期核心资产；`plan/` 与 `tracking/` 是开发脚手架，交付即归档，token 成本高、长期价值低。每次文档产出前先做**档位判定**（L0 轻量 / L1 精简 / L2 全量），避免"小任务走大流程"。

> **目录约定**：AI 过程文档统一存放在项目根目录的 **`aidocs/`** 专属目录下，与 `docs/` 彻底隔离——`docs/` 在各项目中常有其他约定用途（VitePress 文档站源码、GitHub Pages 发布目录、面向用户的产品文档等），混用会互相污染。本技能的一切规则仅作用于 `aidocs/`，不触碰 `docs/` 的其他内容。

> **生命周期阶段**：稳定

> **命名说明**：技能名沿用历史遗留 `quadrant`（象限）字样，实际布局为**五维**（reqs / specs / plan / tracking / guide）；对外表述统一按“五维布局”。

## 🎯 触发条件

- **TRIGGER when**:
  - 开始规划新功能，需要判定文档档位、写需求文档、设计文档、执行计划、进度跟踪或使用指南时
  - 用户询问"文档放哪里"、"aidocs/ 目录怎么组织"或"这次任务要不要写文档"
  - 整理混乱的 `aidocs/` 目录，将散落的文档归类到五维结构中
  - 项目存在符合五维结构的旧版 `docs/` 目录，需要迁移到 `aidocs/` 时
  - 检查文档命名是否符合规范（发现日期前缀时强制重构）
  - 向 `AGENTS.md` / `CLAUDE.md` 注入或更新 aidocs 目录结构说明标记块时
  - 处理 `specs/` 下的接口文档子体系（`specs/接口文档/`）：放行模块子索引、原子接口文件命名、元信息表头与全局索引入口（子体系内容维护由 `doc-craftsman` 负责，本技能只做放行与校验）
  - 当作为 `xy-feat` 协同开发工作流的指南产出与文档合规整理阶段（阶段 6，含规则文件注入）被调用时
- **SKIP**: 对项目根目录 `README.md`、`CLAUDE.md` 等全局配置文件的归类整理（注意：向 `CLAUDE.md` / `AGENTS.md` 注入或更新结构标记块不在 SKIP 范围内）；`docs/` 下不属于五维结构的内容（文档站、产品文档等）一律不整理、不移动

## ⚙️ 依赖与先决条件

- 项目根目录可写；`aidocs/` 不存在时由本技能创建。
- Git 版本控制（用于追踪文件移动历史）。运行 `git --version` 确认。
- 运行环境假设为类 Unix 终端（示例命令使用 `ls`、`git`）。

## 📖 标准工作流

> **前置闸门**：本技能的任何"产出新文档"类调用（写需求/设计/计划/追踪/指南）必须先执行下方的**文档产出分级判定**，再进入对应阶段；仅做结构整理（迁移、命名校验、规则注入）的调用可直接跳过判定。

### 前置闸门：文档产出分级判定（Doc-Tier Gate）

**使用工具**：向用户提问、读取文件（判断任务规模）

**核心原则**：文档是知识图谱，但知识有层级。`specs/`（契约防腐：架构决策、接口契约、数据模型）与 `guide/`（团队资产：How-to 操作手册）是**长期核心资产**；`plan/`（任务拆解）与 `tracking/`（进度清单）是**开发脚手架**——交付后立即归档或删除，token 成本高、长期价值低。因此先按任务特征判定档位，再决定产出哪些象限，禁止所有任务一律五维全出。

**三档模型**：

| 档位 | 名称 | 适用场景 | 文档产出 |
| :--- | :--- | :--- | :--- |
| **L0** | 轻量（零文档） | Bug 修复、单文件小改动、配置/样式微调、纯文档修正、≤3 步无设计决策 | **不建任何象限文件**；关键决策写入 commit message 或内联注释 |
| **L1** | 精简（核心资产） | 常规功能开发：单模块、单线程、有设计沉淀价值 | `specs/`（核心必产）+ `guide/`（按需）；`plan/`、`tracking/` **对话内维护不落盘** |
| **L2** | 全量（五维全出） | 跨模块/跨包、多 Agent 并行、重大架构决策、新页面新交互、用户明确要求 | 五维全出：`reqs/` + `specs/` + `plan/` + `tracking/` + `guide/` |

**判定决策树**（按序执行，命中即止）：

```
文档档位判定（在产出任何文档前执行）：
├─ 用户明确要求完整五维文档/全流程？ ────► L2 全量
├─ 是否全部命中以下轻量特征？
│   ├─ 属于 Bug 修复 / 配置调整 / 纯样式微调 / 文档修正
│   ├─ 改动 ≤ 3 个文件（或单模块局部）
│   ├─ 无新接口契约 / 无新数据模型 / 无架构决策
│   └─ 无新页面 / 无新交互
│   └─ 全部命中 ──► L0 轻量（零文档）
├─ 是否命中任一全量特征？
│   ├─ 跨模块 / 跨包边界
│   ├─ 使用多 Agent 并行开发（dispatching-parallel-agents）
│   ├─ 产生新的架构决策 / 接口契约 / 数据模型
│   ├─ 含新页面 / 新交互 / 变更有感 UI
│   ├─ 需要正式 plan 供多会话执行
│   └─ 用户明确要求完整文档
│   └─ 任一命中 ──► L2 全量
└─ 其余常规功能（单模块、单线程、有设计沉淀）──► L1 精简
```

**各档落盘矩阵**：

| 象限 | L0 轻量 | L1 精简 | L2 全量 |
| :--- | :--- | :--- | :--- |
| `reqs/` | ❌ | 按需（沿用下方 reqs 决策树） | ✅（沿用下方 reqs 决策树） |
| `specs/` | ❌（决策内联 commit/注释） | ✅ 核心必产 | ✅ 核心必产 |
| `plan/` | ❌ | ❌ 对话内维护 | ✅ |
| `tracking/` | ❌ | ❌ 对话内维护 | ✅（多 Agent 时强制） |
| `guide/` | ❌ | 按需（有团队使用价值才写） | ✅ |

**判定执行要求**：
1. 判定结论需在产出第一个文档前给出，并**向用户说明档位及理由**（一句话即可，如"此任务为单文件 Bug 修复，判定 L0 轻量，不产出独立文档"）。
2. 判定依据不足时（无法确定任务规模/是否跨模块），**先向用户提问确认**，禁止猜测档位。
3. L0/L1 档被跳过的象限内容，按需内联至宿主文档或 commit message（禁止生成空壳文件，见行为护栏）。

### 阶段 0：旧版 docs/ 自动迁移（前置检测）

**使用工具**：目录浏览、命令行/终端（如 `git mv`）、文本搜索

每次激活本技能时，先执行本阶段检测；若项目已是 `aidocs/` 布局或无符合条件的 `docs/`，跳过本阶段。

**Step 1 — 结构判定**：`docs/` 存在时，按以下任一条件判定其"符合五维结构"：
- `docs/` 下存在五维子目录中的 **2 个及以上**（`reqs/`、`specs/`、`plan/`、`tracking/`、`guide/`）
- `docs/INDEX.md` 存在且内容含五维象限链接（如 `reqs/`、`specs/` 相对链接）
- `AGENTS.md` / `CLAUDE.md` 中存在 `<!-- docs-layout-quadrant:start` 旧版标记块

**Step 2 — 占用检测**：判定符合后，检查 `docs/` 是否另有他用：
- 存在 `docs/.vitepress/`、`docs/.vuepress/`、`docs/mkdocs.yml`、`docs/_sidebar.md`、`docs/index.md`（文档站首页）、`package.json` 中构建脚本引用 `docs/` 等文档站特征 → 判定为**混合占用**
- 无上述特征 → 判定为**纯五维目录**

**Step 3 — 迁移执行**：
- **纯五维目录**：整体迁移。列出迁移清单（目录树 + 文件数）并获得用户确认后，执行 `git mv docs aidocs`（未被 Git 跟踪时退化为 `mv` 并说明）。
- **混合占用**：只迁移五维资产。将 `reqs/`、`specs/`、`plan/`、`tracking/`、`guide/`、`.archive/`、`INDEX.md` 逐一 `git mv` 至 `aidocs/` 下，其余内容（文档站等）原样保留在 `docs/`。迁移后在 `docs/` 被占用处（如文档站导航配置）无需做任何修改——本技能不触碰非五维内容。
- 若 `aidocs/` 已存在且与待迁移内容冲突（同名文件），逐文件列出冲突清单请用户裁决（保留新版 / 归档旧版），禁止直接覆盖。

**Step 4 — 引用修复与收尾**：
1. 全文搜索 `docs/reqs`、`docs/specs`、`docs/plan`、`docs/tracking`、`docs/guide`、`docs/.archive`、`docs/INDEX` 的残留引用，修正为 `aidocs/` 下的新路径（含 Markdown 链接与规则文件中的路径）
2. 执行阶段 7，将规则文件中的标记块更新为 aidocs 版（版本号以当前技能版本为准）
3. 纯五维整体迁移后 `docs/` 应为空；若因混合占用残留其他内容属正常，**禁止**为清理而删除非五维内容
4. 向用户输出迁移报告：迁移文件数、修复引用数、保留在 `docs/` 的内容清单

### 阶段 1：命名规范校验（关键前置）

**使用工具**：文件搜索、命令行/终端、编辑文件

扫描 `aidocs/` 下所有 `.md` 文件，**执行命名规范校验**：

**领域主体命名法** — 文件名仅描述模块/领域，**禁止任何日期/时间戳前缀**：
- `<Bad>` `2026-07-15-网关代理转发-design.md` — 一次性产物，AI 无法判断是否为最终状态
- `<Good>` `网关代理转发.md` — 随代码演进的活文档

**优先中文命名** — 文件名优先使用简明中文描述（如 `网关代理转发.md`），便于人类快速识别文档主题。英文 kebab-case 作为备选（如 `gateway-proxy-design.md`），适用于技术性强的模块或国际化项目。

发现违规文件时，先列出重命名清单并**获得用户确认**，再使用 `git mv` 执行，并修复所有引用该文件的内部链接。

**同名冲突处理**：当多个日期前缀文件去日期后解析为同一目标文件名时（如 `2026-07-15-网关设计.md` 和 `2026-07-20-网关设计.md` 都想去重为 `网关设计.md`），按以下规则仲裁：

1. **识别冲突**：去日期前缀后，检测是否有 2+ 个文件映射到同一目标名
2. **选主版本**：按日期从文件名中提取并比较，**保留最新日期**的那个作为主版本（使用目标名）
3. **归档旧版**：较旧的版本追加 `-archived` 后缀，移入统一归档目录 `aidocs/.archive/{象限}/`：
   ```
   aidocs/specs/网关设计.md                       ← 最新版（2026-07-20 的内容）
   aidocs/.archive/specs/网关设计-archived.md     ← 旧版（2026-07-15 的内容）
   ```
4. **版本合并提示**：冲突解决后，向用户报告：
   > "发现 N 个同名文档的多个日期版本，已保留最新版 `网关设计.md`，旧版已归档至 `aidocs/.archive/`。请确认是否需要将旧版中的独有内容合并到新版中。"
5. 若文件名中无日期可比较（如 `网关设计.md` 和 `网关设计-v2.md` 同时存在），优先保留无后缀版本，将 `-v2` 版归档

### 阶段 2：五维归类

**使用工具**：命令行/终端（如 `git mv`）、编辑文件

根据文档类型分配到对应子目录：

| 象限 | 路径 | 定位 | 生命周期 |
| :--- | :--- | :--- | :--- |
| 需求文档 | `aidocs/reqs/` | 产品需求描述（PRD），记录 **What**——页面功能、交互流程、业务规则，是设计文档的输入 | **中长周期** — 功能验收后冻结，作为业务知识长期保留；若需求被废弃则归档至 `aidocs/.archive/reqs/` |
| 设计规范 | `aidocs/specs/` | 技术架构决策（ADR），系统的"宪法"，记录 **Why**——架构选型理由、接口设计、数据模型 | **长周期**，随代码演进持续更新 |
| 执行计划 | `aidocs/plan/` | 实施计划与任务拆解，开发前的 Draft | **短周期** — Feature 交付后追加 `-archived` 并归档至 `aidocs/.archive/plan/` |
| 进度跟踪 | `aidocs/tracking/` | 任务 Checklist | **超短周期** — 任务验收后归档至 `aidocs/.archive/tracking/` 或删除 |
| 使用指南 | `aidocs/guide/` | 面向开发者的 How-to 操作手册 | **长周期**，随功能迭代更新 |

**弹性降级决策树**：经**前置闸门档位判定**后，档位决定象限集合；在同一档位内，`reqs/` 和 `tracking/` 仍为按需维度，AI 必须按以下决策树判定（L0 档不落任何文档，直接跳过本节）：

#### `reqs/` 判定决策树

```
是否创建 aidocs/reqs/<功能名>-req.md？
├─ 用户明确要求编写/整理需求文档？ ───► ✅ 创建
├─ 属于纯技术重构/性能优化/API对齐？ ──► ❌ 跳过，需求背景内联至 specs/
├─ 包含新页面、新业务交互或变更有感UI？──► ✅ 创建
└─ 其他无法裁决场景 ───────────────► 向用户提问确认
```

#### `tracking/` 判定决策树（仅 L2 全量档内生效）

```
是否创建 aidocs/tracking/<功能名>.md？（L1 精简档一律不落盘，进度对话内维护）
├─ 使用了 dispatching-parallel-agents？──► ✅ 强制创建（防多 Agent 并发写入冲突）
├─ 单线程任务且卡片/步骤 ≤ 3 个？ ────► ❌ 跳过，进度 Checklist 内联至 plan.md 尾部
└─ 其他独立任务场景 ───────────────► 默认创建（宁可多建，不漏追踪）
```

> **核心资产**：`specs/` + `guide/` 为长期核心资产（L1 档必产 specs、guide 按需；L2 档全产）；`plan/` + `tracking/` 为开发脚手架，仅在 **L2 全量档**落盘，L1 档对话内维护不落盘。任何档位均不得产出空壳文档。

### 阶段 2.5：specs 子结构——接口文档体系（v3.3 放行）

`aidocs/specs/` 下允许**接口文档子体系**（维护归 `doc-craftsman`，本技能只做放行与校验）：
- 目录 `aidocs/specs/接口文档/{domain}/` + 域总索引 `specs/接口文档/INDEX.md`（按模块分组，文档多时仅一行跳转）；原子文件 `{module}-{sub}-{action}.md`（**命名豁免**：英文 kebab-case）；模块子索引 `{domain}/INDEX.md` 含「架构与业务约定」共享约定下沉节。
- 文档头允许「元信息表」替代 YAML 最小头（**frontmatter 豁免**，以项目接口文档规范为准）；全局索引仅「接口文档」域入口一行（**覆盖放行**）；接口文档属 specs 核心资产，不随 plan/tracking 归档。

### 阶段 3：机器可读文档头与生命周期管理

**Agent-Friendly 最小头**：所有新建的 `aidocs/` 功能文档（`INDEX.md` 除外）必须在 H1 前携带 YAML frontmatter，用于跨会话状态恢复与机械校验：
必填字段为 `status`、`tier`、`domain` 和 `updated_at`；有明确来源时加 `source_workflow`。状态必须随审批、交付和归档显式演进。执行阶段 3 或创建功能文档前，读取 `references/agent-friendly.md` 获取字段模板与状态语义。

**使用工具**：目录浏览、命令行/终端（如 `git mv`）

对已有文档执行过期清理：

1. **plan/** — 扫描已完成功能的 plan 文档：
   - 已交付 → 追加 `-archived` 后缀，移入 `aidocs/.archive/plan/`
   - **内联降级处理**：若 plan 文档尾部包含内联的 `## 📋 实施进度 Checklist`，则随 plan 文档整体归档（无需单独拆分）
   - AI 不应再将已完成的 plan 作为系统现状参考源
2. **tracking/** — 扫描已验收的追踪文档：
   - 独立 tracking.md → 按以下决策树处理：
     - 包含设计讨论/决策记录 → 移入 `aidocs/.archive/tracking/`
     - 纯勾选框清单，无讨论价值 → 直接删除（需先向用户说明并获得确认）
   - **代码库不该存储执行状态**，Git 历史已足够
3. **reqs/** — 扫描需求文档：
   - 功能已验收 → 保持原位（作为业务知识长期保留）
   - 需求已废弃（功能下线或被替代）→ 追加 `-archived` 后缀，移入 `aidocs/.archive/reqs/`
4. **specs/ & guide/** — 作为长周期文档，保持原位，但检查内容是否过时。
5. **frontmatter 校验** — 检查 `status`、`tier` 和 `updated_at` 与实际路径及生命周期一致；旧文档缺失字段时不强制批量改写，可在下次实质性修改时补齐。**豁免**：`specs/接口文档/` 子体系内的原子接口文件允许元信息表头替代 YAML frontmatter（见阶段 2.5），不做本校验。

### 阶段 4：建立知识索引

**使用工具**：写入文件、读取文件

在 `aidocs/` 根目录维护 `INDEX.md`（若不存在则创建），作为 AI 和人类的知识入口：

```markdown
# 📚 项目知识索引

> 本文件是 aidocs/ 目录的导航入口，按业务领域组织。新增文档时必须同步更新此索引。

## [领域名称]
| 文档 | 象限 | 文件 |
| :--- | :--- | :--- |
| 网关代理转发需求 | reqs | [gateway-proxy-req.md](reqs/gateway-proxy-req.md) |
| 网关代理转发设计 | specs | [gateway-proxy-design.md](specs/gateway-proxy-design.md) |
| 网关使用指南 | guide | [gateway-proxy-guide.md](guide/gateway-proxy-guide.md) |

## 📦 归档文档
> 仅列出仍有参考价值的归档文档（如被替代的旧版设计），纯 tracking 清单不列入。
| 文档 | 原象限 | 归档原因 | 文件 |
| :--- | :--- | :--- | :--- |
| 网关设计 v1 | specs | 被 v2 替代 | [.archive/specs/网关设计-archived.md](.archive/specs/网关设计-archived.md) |
| 网关需求 v1 | reqs | 需求废弃 | [.archive/reqs/网关需求-archived.md](.archive/reqs/网关需求-archived.md) |
```

每次新增/删除/重命名文档后，**必须同步更新** `aidocs/INDEX.md`。归档文档移入 `aidocs/.archive/` 时，若有参考价值也需在 INDEX 的"📦 归档文档"小节中体现。

**索引完整性校验**：

1. `INDEX.md` 中每个 Markdown 相对链接必须指向存在的文件。
2. 五个象限目录中每个非归档功能文档都必须在 `INDEX.md` 至少出现一次（**豁免**：`specs/接口文档/` 子体系内的原子接口文件不逐条要求，以「接口文档」域级入口一行计，见阶段 2.5）。
3. 更新索引时按象限统计现存非归档文档数量；若某象限为空，写明"暂无文档"，禁止让读者从缺失小节猜测目录是否为空。
4. 无法执行脚本校验时，至少用文本搜索核对链接路径和遗漏文件，并在完成汇报中说明校验方式。

> **归档小节规模控制**：`📦 归档文档` 小节只保留分类概括或极少数仍有重大参考价值的历史链接，**总行数 ≤ 5 行**，禁止展开长列表（紧凑化重构由 `lean-docs` 的索引紧凑化重构阶段执行）。

### 阶段 5：移动文件与修复链接

**使用工具**：命令行/终端（如 `git mv`）、文本搜索、编辑文件

1. 使用 `git mv <旧路径> <新路径>` 移动文件（保留 Git 历史）；若 `aidocs/` 未被 Git 跟踪（如被 `.gitignore` 忽略），退化为普通 `mv` 并向用户说明
2. 搜索文档中引用了旧路径的链接，逐个修正为新的相对路径
3. 所有文档间链接必须使用相对路径（如 `../specs/xxx.md`），**禁止**使用绝对路径

### 阶段 6：验证

**使用工具**：文本搜索

搜索：
- 旧路径残留 → 确认所有引用已更新
- 日期前缀残留（`20[0-9]{2}-[0-9]{2}-[0-9]{2}-.*\.md`）→ 确认已全部重命名
- INDEX.md 中的链接 → 确认全部可访问

### 阶段 7：向项目规则文件注入 aidocs 结构说明

**使用工具**：读取文件、写入文件

检查项目根目录是否存在 `AGENTS.md` 和/或 `CLAUDE.md`，向其中追加标准化的 aidocs 目录结构说明段落，帮助 AI 助手在后续会话中理解文档组织规范。

**注入策略与授权**：
1. 读取目标文件，使用正则 `<!-- docs-layout-quadrant:start.*-->` 匹配检查是否已包含标记（忽略版本号后缀，如 `(v2.5)` 或 `(v3.0)`）
2. 若已存在 → 替换整个标记块至 `<!-- docs-layout-quadrant:end -->`（同步刷新 `start` 标记行中的版本号后缀为最新 `(vX.Y)`），保持标记块在文件中的原始位置不动，严禁重复追加
3. 若不存在 → 在文件末尾追加标准化段落
4. **确认要求**：独立调用本技能时，修改规则文件前需先向用户简要说明要写入/更新的标记块内容；在 `xy-feat` 工作流上下文中，用户调用 `/xy-feat` 视为预授权规则文件标记块的标准化注入与更新

**注入内容模板**：执行注入前，读取 `references/injection-template.md` 获取完整注入内容模板（含 `start` / `end` 标记与当前版本号）；该文件仅在执行阶段 7 注入时读取。

**注意事项**：
- 不改动标记块之外的任何已有内容；首次注入时在文件末尾追加，更新时已存在的标记块（连同 `start` 标记行上的版本号）整体替换
- 若目标文件不存在，跳过该文件（不强制创建 AGENTS.md / CLAUDE.md）
- 标记中的版本号取技能 version 的主.次版本号（如 `3.0.0` → `v3.0`），用于后续版本升级时定位和替换，不要手动删除标记注释

## ⛔ 行为护栏

- **🚫 禁止日期前缀 + 优先中文命名**：文件名不得以日期开头，必须使用领域主体命名（如 `网关代理转发.md`）。优先使用简明中文描述，英文 kebab-case 作为备选。发现违规时必须重命名并修复引用。文档是知识图谱，不是流水账。
- **必须使用相对路径**：文档间互相引用时，必须使用相对路径（`./` 或 `../`），禁止使用任何绝对路径
- **🚫 专属目录边界**：五维文档只能写入 `aidocs/`，禁止向 `docs/` 新建过程文档；反之，`docs/` 中非五维内容（文档站、产品文档等）一律不整理、不移动、不删除
- **禁止散落文档 + 保护入口文件**：`aidocs/` 根目录下只能保留 `INDEX.md` 等入口文件，所有功能性文档必须归入五个子目录。移动和重命名文档时，确保项目根目录的 `README.md` 不受影响。`AGENTS.md` / `CLAUDE.md` 仅由阶段 7 通过标记块方式修改，其他阶段不得编辑
- **规则文件注入标记不可损坏 + 注入须有授权**：阶段 7 注入的 `<!-- docs-layout-quadrant:start (vX.Y) -->` / `<!-- docs-layout-quadrant:end -->` 标记用于版本升级时定位和替换，任何其他操作不得删除或修改这两个标记之间的内容。修改 `AGENTS.md` / `CLAUDE.md` 前需向用户说明（在 `/xy-feat` 工作流下视作预授权）
- **必须使用 `git mv` 保留 Git 历史**：移动已被 Git 跟踪的文件时必须使用 `git mv` 而非普通 `mv`，以完整保留版本变更历史；未跟踪文件（如 `aidocs/` 被 `.gitignore` 忽略时）退化为普通 `mv` 并向用户说明
- **删除/批量移动前需确认**：任何删除或批量移动、重命名文件的操作，必须先列出受影响文件清单并获得用户确认后方可执行（阶段 0 的整体迁移同样适用）
- **🚫 禁止空壳文档**：经档位判定跳过某象限时，禁止强行生成空白/空壳 `.md` 文件占位。L0 档不建任何文档；L1 档被跳过的象限（plan/tracking）内容对话内维护；降级内容必须使用标准内联模板写入宿主文档
- **L1 状态必须可恢复**：L1 的 plan/tracking 虽不独立落盘，但阶段出口、任务清单变更和最终结果必须写入对应 `aidocs/specs/<功能名>-design.md` 的 `## Execution State` 节；禁止只保留在易失对话历史中
- **档位判定先行且不可跳过**：任何产出新文档的调用必须先完成前置闸门档位判定并向用户说明档位；禁止不判定直接全量五维产出（L0 任务走全量流程 = 资源浪费），也禁止不判定直接零文档（L2 任务零文档 = 知识流失）
- **索引同步不可跳过**：任何文档增删改后，必须同步更新 `aidocs/INDEX.md`，保持导航网最新并完成相对链接完整性校验

### <Good> 分级判定范例（Doc-Tier Gate 应用）

**<Bad> — 反模式：小任务走全量流程 / 大任务零文档**

```markdown
# ❌ 单文件 Bug 修复也五维全出
任务：修复登录接口超时导致 500 的错误（改动 1 个文件、1 处逻辑）
错误做法：
- aidocs/reqs/login-timeout-req.md       ← 空壳 PRD，无任何业务需求
- aidocs/specs/login-timeout-design.md   ← 无架构决策，仅复述代码
- aidocs/plan/login-timeout-plan.md      ← 交付即归档，token 白耗
- aidocs/tracking/login-timeout.md       ← 3 个勾选框，验收即删除
- aidocs/guide/login-timeout-guide.md    ← 无对外使用价值
问题：五份文档全是脚手架，长期资产为零，token 消耗却放大数倍。
```

```markdown
# ❌ 跨模块架构改造零文档
任务：拆分子订单服务，涉及订单/支付/库存三模块 + 并行子代理
错误做法：直接改代码，无 specs 契约、无 plan 任务拆解、无 tracking 并发追踪
问题：架构决策无记录（契约防腐缺失），多 Agent 并发无追踪（进度失控）。
```

**<Good> — 规范做法：按档位产出**

```markdown
# ✅ L0 轻量（单文件 Bug 修复）
- 判定：改动 1 文件、无新契约/架构决策 → L0 零文档
- 产出：commit message 记录根因与修复方式；不建任何 aidocs/ 文件

# ✅ L1 精简（常规单模块功能）
- 判定：单模块、单线程、有设计沉淀 → L1 精简
- 产出：
  - aidocs/specs/pagination-design.md   ← 核心必产（接口契约、选型理由）
  - aidocs/guide/pagination-guide.md    ← 按需（新组件有团队使用价值才写）
  - plan/tracking 不落盘：任务拆解与进度在对话内维护

# ✅ L2 全量（跨模块架构改造 + 多 Agent 并行）
- 判定：跨 3 模块 + 并行子代理 → L2 全量
- 产出：五维全出 reqs + specs + plan + tracking + guide（tracking 为并发安全强制创建）
```
