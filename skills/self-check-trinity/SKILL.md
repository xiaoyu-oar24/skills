# self-check-trinity

> **生命周期阶段**：稳定

## 🎯 触发条件

- **TRIGGER when**:
  - 完成代码修改，准备提交或发起 PR 时
  - 被要求执行"验证"、"自检"、"交付"或"收尾"时
  - 修复 Bug 并准备标记为完成时
- **SKIP**: 仅修改文档、注释或 README，不涉及运行时代码时

## ⚙️ 依赖与先决条件

不限定具体技术栈或要求预先配置全部三项能力。先读取项目规则、构建配置、脚本和 CI，确定各项是否适用及实际命令；缺少命令或依赖不等于不适用。

**校验与诊断命令**：
- 包管理器探测：可通过运行 `ls pnpm-lock.yaml || ls package-lock.json || ls Cargo.toml || ls pyproject.toml` 等确认项目环境。
- 可通过执行 `git status` 确认当前有需要验证的代码变更。
- 运行环境假设为类 Unix 终端（示例命令使用 `ls`、`git`）。

## 📖 标准工作流

按 lint → typecheck → test 顺序评估并执行适用项，逐项记录状态和证据。失败或环境阻塞不得记为通过。

### 阶段 0：识别项目类型与命令

在执行检查前，通过以下方式确定具体命令：

1. 查看项目根目录的构建配置文件，识别技术栈与对应包管理器，确定可执行指令。
2. 查看配置文件、项目规则及 CI，确认实际脚本、工具和强制检查要求；命令名称有差异时以项目配置为准。没有包装脚本但已有检查工具时，使用项目配置对应的直接命令。
3. 按下表判定每项状态。无法确认适用性或缺少必需命令时，先记录环境阻塞及已查证依据；继续其他可运行检查，仅就无法从项目材料确定的问题向用户询问。

| 状态 | 判定条件 | 必须记录 |
| :--- | :--- | :--- |
| 通过 | 实际运行适用命令且检查成功 | 命令、退出码及有效检查结果；空跑或未发现测试不得当作测试通过 |
| 失败 | 检查已执行并发现代码、类型或测试问题 | 命令、错误摘要及修复结果 |
| 环境阻塞 | 适用项因依赖、网络、权限、配置缺失等无法有效执行，或适用性尚未确认 | 阻塞原因、已检查的配置路径及需要补齐的条件 |
| 不适用 | 项目规则未要求该项，且技术栈、配置和变更范围能证明该项不适用 | 配置路径、变更范围及不适用理由；例如未启用任何类型检查的纯 JavaScript 项目可不适用 typecheck |

**出口判定**：至少一项通过，且其余项均通过或有依据的不适用，才可报告“适用检查通过”并进入后续流程；有失败或环境阻塞则不得通过质量闸门。三项均不适用时，只能报告“无适用检查，未验证”，需明确替代验证方案；不得据此宣称代码质量已验证。不适用不记为通过，不得覆盖项目强制检查要求。

### 阶段 1：Lint 检查

若适用，执行项目对应的 lint 命令。如有报错，定位原因并按护栏处理；不适用时记录依据。

### 阶段 2：类型 / 编译检查

若适用，执行项目对应的类型或编译检查命令，不能以 Lint 结果替代；不适用时记录依据。如果报错涉及第三方 API 改名，可通过技能调用执行 `api-name-drift-defense` 辅助排查（该技能的回归验证不会级联回调本技能，调用环已显式闭合）。

### 阶段 3：测试

若适用，执行项目测试命令并确认实际运行了相关测试；不适用时记录依据。输出三项状态及总判定，不能将“没有测试框架”或“未发现测试”直接记为不适用或通过。

## ⛔ 行为护栏

- **禁止绕过适用检查**: 任一适用项失败或环境阻塞，禁止提交代码；禁止使用 `--no-verify` 或等效手段跳过 Git hooks
- **三项均须评估**: Lint 通过不能替代类型检查或测试；不适用必须有依据，缺少脚本、依赖或测试框架不能直接作为豁免
- **环境问题如实上报**: 环境阻塞与失败均不得改写成通过或不适用；最终报告保留未通过项及原因
- **有界重试**: 遵守用户或项目的重试上限；未指定时，同一问题仅在修正参数、环境或实现后重试一次，再失败则停止该项并上报，不重复空跑
- **先检测再执行**: 禁止不经检测就假定命令名称，必须按照阶段 0 的流程确认后再执行

## 📝 模板与范例

### <Bad>

- 纯 JavaScript 项目没有 typecheck 脚本，就把类型检查记为“通过”；或将缺依赖导致的测试启动失败记为“不适用”。

```bash
# 错误：只跑 Lint 就跳过后续检查直接提交
npm run lint
git commit -m "fix: something" --no-verify
```

### <Good>

```text
# 纯 JavaScript 项目示例：读取 package.json、jsconfig.json 和 CI，确认未启用类型检查且无强制要求
Lint：通过（项目 lint 命令退出码 0）
Typecheck：不适用（未启用 checkJs 或其他类型检查，变更仅涉及 JavaScript）
Test：通过（项目测试命令退出码 0，实际执行的相关测试通过）
结论：适用检查通过；类型检查不适用，不计入通过项。
```

> 以下示例以 pnpm 为例。执行前应先通过项目根目录下的锁文件探测实际包管理器（`pnpm-lock.yaml` → pnpm / `yarn.lock` → yarn / `package-lock.json` → npm），替换为对应命令。

```bash
# Node 项目示例
pnpm run lint
pnpm run typecheck
pnpm run test
```

```bash
# Python 项目示例
ruff check .
mypy src/
pytest
```

```bash
# Rust 项目示例
cargo clippy -- -D warnings
cargo check
cargo test
```

```bash
# Java Maven 项目示例
mvn checkstyle:check
mvn compile
mvn test
```
