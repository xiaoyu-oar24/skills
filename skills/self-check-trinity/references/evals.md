# self-check-trinity 触发评测集

> 评估驱动开发：修改 `description` 或触发条件后，用以下提示词回归验证路由行为。

## 应触发（Expected：激活）

1. "功能写完了，帮我验证一下再提交"
2. "这个 bug 修好了，做个收尾自检"
3. "准备提 PR 了，跑一遍质量检查"

## 不应触发（Expected：跳过）

1. "帮我改一下 README 里的错别字"（仅文档变更）
2. "给这个函数补几行注释"（仅注释变更）
3. "刚开始写这个功能，先帮我搭个文件结构"（开发尚未完成）

## 适用性与检查状态评测

| 场景 | 预期判定与出口 |
| :--- | :--- |
| 纯 JavaScript 项目未启用 checkJs/其他类型检查，项目规则与 CI 无类型检查要求；lint/test 实际通过 | Typecheck 不适用，附配置与变更范围依据；报告“适用检查通过”，不声称三项全通过 |
| 没有 typecheck 脚本，但 tsconfig 和 CI 已配置 tsc 检查 | Typecheck 适用，运行项目配置对应的直接命令，不能标记不适用 |
| Typecheck 脚本存在，但 TypeScript 依赖未安装 | 环境阻塞；保留配置路径与缺失依赖，不得以不适用放行 |
| 测试启动时网络或权限报错 | 环境阻塞；继续其他可运行检查，质量闸门不通过 |
| 测试实际运行并出现断言失败 | 失败；有界修复重试，未解决则报告，不进入提交 |
| 测试命令退出码为 0，但没有发现或运行任何测试 | 不记为测试通过；检查发现规则与测试范围，无法有效执行时记环境阻塞 |
| 项目没有任何检查脚本或测试框架，也没有豁免依据 | 适用性尚未确认，记录环境阻塞；不能将三项全部记为不适用 |
| 三项均有项目规则与范围依据判为不适用 | 报告“无适用检查，未验证”，明确替代验证方案，不宣称质量检查通过 |
| 项目明确要求 typecheck，但本地未配置命令 | 环境阻塞，查证项目要求并补齐必要条件；不得以纯 JavaScript 为由豁免 |
