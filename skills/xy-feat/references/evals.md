# xy-feat 触发评测集

> 评估驱动开发：修改 `description` 或触发条件后，用以下提示词回归验证路由行为。本技能刻意收窄为仅显式调用，"不应触发"用例与"应触发"同等重要。

## 应触发（Expected：激活）

1. `/xy-feat 做一个文件上传功能`
2. `/xy-feat`（空需求，预期先追问"你要做什么功能？"）
3. `/xy-feat 给网关加代理转发，用隔离 worktree 开发`

## 不应触发（Expected：跳过）

1. "开发一个新功能"（自然语言描述，未显式输入 `/xy-feat`）
2. "帮我写一个用户登录特性"
3. "这个 xy-feat 技能的文件在哪个目录？"（询问技能本身，不是调用工作流）
4. "lean-docs 跳过了这个开发任务，帮我继续实现登录接口" → 按项目常规流程执行，相邻技能分流不构成 `/xy-feat` 显式调用。

## 档位判定专项评测（阶段 0 Doc-Tier Gate）

> 以下用例验证阶段 0 档位判定的正确性——触发后应产出对应档位的文档，而非一律五维全出。

### 应判定 L0 轻量（零文档，不建任何 aidocs/ 文件）
1. `/xy-feat 修复登录接口超时 500，只改一个文件`
2. `/xy-feat 把按钮颜色改成灰色，纯样式微调`

### 应判定 L1 精简（specs + guide 按需，plan/tracking 不落盘）
1. `/xy-feat 重构分页组件内部的数据合并逻辑，单模块单 Agent，无新交互或重大架构决策`
2. `/xy-feat 给用户模块新增内部接口契约和数据模型，单 Agent，无跨模块影响、重大架构决策或新交互` → L1，新增契约本身不触发 L2。

### 应判定 L2 全量（五维全出）
1. `/xy-feat 拆分子订单服务，涉及订单/支付/库存三模块`
2. `/xy-feat 这个功能要用多子代理并行开发，走完整文档流程`
3. `/xy-feat 修改订单与支付之间的共享接口契约，只改两个文件` → L2，跨模块契约变更优先于文件数量。

## Agent-Friendly 恢复专项评测（v5.5）

1. `/xy-feat 继续上次的 L1 功能开发` → 应先读取 specs 的 `Execution State`；缺失时根据现有证据重建，只有授权来源或关键范围无法查证时才询问缺失项，不重走完整审批链。
2. `/xy-feat 设计文档批准后中断了，现在继续` → 应从 specs frontmatter 和 `Execution State` 恢复到阶段 2 或之后实际完成点。
3. `/xy-feat 收尾时检查文档合规` → 应校验最小 frontmatter、生命周期状态、INDEX 链接和五象限覆盖。

## 接口契约拆分专项评测（v5.7）

1. `/xy-feat 实现供应商准入管理，含 6 个接口，接口契约部分设计文档超过 400 行` → 阶段 6 应调用 `doc-craftsman` 将接口契约拆分为 `aidocs/specs/接口文档/supplier/` 原子文件并维护三级索引，design.md 保留架构决策与接口总览链接。
2. `/xy-feat 实现一个单接口小功能` → 阶段 6 接口契约未超阈值，不触发拆分，跳过 `doc-craftsman`。
3. `/xy-feat 接口文档很多但 doc-craftsman 技能不可用` → 阶段 6 应跳过拆分并在汇报中注明一行，不视为违规。

## 质量检查出口评测

1. L0 纯 JavaScript 改动，lint/test 实际通过，项目配置与规则确认未启用类型检查 → 阶段 4 记录 typecheck 不适用，报告“适用检查通过”后进入阶段 5；优先与降级流程结论相同。
2. 测试因缺依赖无法启动 → 阶段 4 记录环境阻塞，不进入阶段 5，不改写为不适用。
3. 三项均有依据判为不适用 → 报告“无适用检查，未验证”，明确替代验证方案，不自动进入阶段 5。
4. 本地仅有 self-check-trinity v1.0.3 或该技能不可用 → 读取阶段 4 降级文件执行兼容校验，按相同四态出口判定，不以技能缺失代替实际检查。

## v6 执行档位与授权回归

| 场景 | 可观察的预期行为 |
| :--- | :--- |
| `/xy-feat 把按钮颜色按已明确的设计值调整` | L0：一次说明目标/范围/验证方式后执行；无独立命名、设计或计划审批，无 aidocs 文件，无独立设计/规划技能调用 |
| L1 单模块方案明确，用户已授权实现 | 方案与精简清单一起呈现，维护 specs 状态并连续执行；不再分别批准设计和计划 |
| L2 设计已获批，计划未改变范围 | 自审计划后继续实现，不要求再次批准相同决策；落盘计划与追踪仍保留 |
| 用户只批准设计，没有授权提交 | 实现和验证继续；不自动 git commit/push，不将技术审批写成 Git 预授权 |
| 用户已授权提交并创建 PR，目标分支明确 | 阶段 6 完成后在阶段 7 直接执行对应操作，不再重复提问；不顺带合并或删除 worktree |
| 实现发现需删除现有文件，原授权未覆盖该清单 | 列明影响并等待明确确认；不能用“减少确认”绕过不可逆操作边界 |
| 独立设计技能要求逐节审批，现有授权已覆盖 | 主编排传入已有授权并合并交互，不重复审批；真正未决的重大取舍仍需确认 |
| 恢复会话时有“已授权推送”的快照但无可查证来源 | 先完成独立的检查/审查，仅对推送权限确认，不能伪造授权或重跑全部设计流程 |

## v6 验证证据与集成顺序回归

| 场景 | 可观察的预期行为 |
| :--- | :--- |
| 检查运行前后输入发生变化 | 不把检查后快照当作已验证证据；查明变化并重验受影响项 |
| HEAD 相同，但未暂存源码被改 | 当前快照与验证基线不同，重跑受影响检查 |
| 文件一直显示 M，期间内容再次修改 | 内容摘要发现变化，不依赖状态文本去重 |
| 同名未跟踪测试文件内容被改 | 快照发现内容变化，审查与验证覆盖该文件 |
| 源码已删除/重命名，或可执行位变化 | 识别路径/模式差异并判断影响，不复用失效证据 |
| 仅重新暂存或提交，工作区内容与环境不变 | 核对暂存树后可复用证据；不能只因 SHA 不同强制重跑 |
| 工作区已验证，但暂存区仍是旧实现 | 不声称待提交树通过；修正暂存范围或单独验证预期提交树 |
| 阶段 6 只增加不参与构建的使用指南 | 审查新文档并做链接/结构检查；无需机械重跑业务全量测试 |
| 阶段 6 修改 MDX、技能指令、锁文件或测试配置 | 不按后缀或“文档阶段”豁免；重跑相应验证，影响不明则全部适用检查 |
| 环境变化、快照遗失、子模块/外部链接或忽略输入未被覆盖 | 不能证明证据有效，补足可靠证据或重新验证 |
| 阶段 5 Important 修复改变源码 | 重验受影响项并审查修复后才进入阶段 6 |
| 阶段 6 已归档 plan/tracking，随后准备 PR | 阶段 7 使用更新后的路径和交付清单，PR 包含指南/索引/归档，不要求旧路径存在 |
| 用户只要求实现功能 | 阶段 7 汇报本地结果，不强制四选一，也不自行提交或推送 |
| 合并或解决冲突后最终树改变 | 验证最终树，确认结果后才报告集成完成；未授权时保留 worktree |
