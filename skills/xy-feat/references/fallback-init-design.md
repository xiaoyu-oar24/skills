# xy-feat 降级流程：阶段 0（隔离开发）与阶段 1（方案设计）

> 隔离开发载体不可用，或 L1/L2 未使用独立设计技能时按需读取对应段落；遵循正文“执行档位与授权复用”。L0 不加载完整设计流程，只需目标、范围和验证方式的简短说明。

## 阶段 0 降级：隔离开发（可选）

当用户提到"隔离开发"或当前工作区已有未提交变更时：

```
步骤 1：检测当前环境
  git rev-parse --show-toplevel  → 确认在 git 仓库中
  git branch --show-current      → 确认当前分支

步骤 2：确认隔离需求与已有授权
  用户已要求隔离时直接准备；仅有既存改动时先判断能否安全共存，不能覆盖、暂存或搬走用户改动

步骤 3：隔离确有必要且属于已授权任务时执行；路径冲突或越界权限不足时仅询问缺失项
  mkdir -p .worktrees
  git worktree add .worktrees/<功能名> -b codex/<功能名>
  cd .worktrees/<功能名>

步骤 4：验证基线
  npm test / cargo test / pytest
```

创建前检查目标目录和分支无冲突、worktree 目录不会被误跟踪；遵循项目分支前缀，示例使用 Codex 默认 `codex/`。若平台已有原生隔离工具，优先使用原生工具。

## 阶段 1 内联流程：方案设计

### 1.1 需求澄清（草案优先，仅在歧义时提问）

- 阅读项目现有文件、文档、最近提交，理解当前上下文。
- 若需求模糊，向用户提问以细化需求，**多选优先于开放式**，提问做到精准不冗余：
  - 目标是什么？成功标准？
  - 有什么约束条件（技术栈、性能、兼容性）？
  - 与现有系统的接口关系？
- 若需求包含多个独立子系统，先协助用户拆分为子项目，单独走 xy-feat 流程。

### 1.2 按复杂度选择方案

- 沿用项目已有方案即可满足需求时直接说明选用理由；存在真实重大取舍时才比较 2-3 种可行方案，集中列出需用户决定的问题。

### 1.3 一次呈现方案与清单

- **拒绝逐节打断**：将方案全貌整理为一份完整的结构化设计 Draft，一次性展示（架构、组件、数据流、错误处理、测试策略）：
  - 简单部分：几句话概括
  - 复杂部分：200-300 字详细说明与代码伪代码
- 仅在遇到**重大底座选型冲突**（如 2-3 种完全对立的技术架构选型）时才单独提问确认，其余情况下直接呈现 Draft；已有实现授权且无重大未决事项时继续执行，不等待形式审批。
- **设计隔离原则**：每个模块应有明确边界和接口，可独立理解和测试。

### 1.4 撰写设计文档

- 仅 L1/L2 将设计写入 `aidocs/specs/<功能名>-design.md`；L0 不创建 specs。
- 文件 H1 前添加 Agent-Friendly 最小头（`status`、`tier`、领域名、更新日期、`source_workflow: xy-feat`）；状态如实记录：仅设计确已获批时为 `approved`，未单独批准的设计保留 `draft`，执行权限另记授权来源，不伪造审批。
- **reqs/ 内联降级要求**：若经决策树判定（如纯技术重构/优化）跳过独立 `aidocs/reqs/` 需求文档，必须在 `aidocs/specs/<功能名>-design.md` 的头部包含【`## 1. 需求背景与改造目标`】章节，明确背景与问题定义。
- 文档应包含：需求背景与改造目标（降级时必填）、方案选择理由、架构设计、接口定义、数据模型、测试策略。

### 1.5 设计文档自审

写完后以新视角快速自审：
1. 占位符扫描：是否有 "TBD"/"TODO"/未完成的章节？
2. 内部一致性：不同章节之间是否有矛盾？
3. 范围检查：是否聚焦足够，还是需要进一步拆解？
4. 歧义检查：是否有任何需求可被两种方式解读？

自审通过后新增或刷新 `## Execution State`，记录阶段、任务范围和授权来源。已有授权覆盖且无关键未决问题时进入阶段 2；不得在 Draft 已获确认后再次要求批准同一份 spec。
