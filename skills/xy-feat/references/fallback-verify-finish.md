# xy-feat 降级流程：阶段 4（验证）、阶段 5（审查）与阶段 7（最终交付/集成）

> 本文件在 superpowers 对应技能（`verification-before-completion` / `requesting-code-review` / `finishing-a-development-branch`）不可用时按需读取；`self-check-trinity` 旧于 v1.1.0 或不可用时，仅按需读取阶段 4。质量检查优先使用本地 `self-check-trinity`，无四态能力时使用下方兼容流程，不依赖 superpowers。

## 阶段 4 内联流程：验证完成

### The Iron Law

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

在没有运行验证命令并看到输出之前，**禁止**声称"通过"、"完成"、"没问题"。

### 验证流程

1. **档位适配**：L2 档所有任务卡片在 `aidocs/tracking/<功能名>.md` 中标记为 `✅` 后，通过技能调用 `self-check-trinity`；L1 档以对话内任务清单全部 `✅` 为准；L0 档跳过任务清单校验，直接进入质量检查：
   - 自动识别项目技术栈，读取项目规则、构建配置和 CI，确定 lint / typecheck / test 的适用性与实际命令
   - 依次执行适用检查，逐项记录通过、失败、环境阻塞或不适用及依据；重试上限遵循该技能及用户/项目要求
   - 兼容旧版/缺失技能时：命令实际有效执行并成功为通过，发现代码或测试问题为失败，缺命令/依赖/权限或适用性不明为环境阻塞；不适用须有技术栈、配置和变更范围依据且不得覆盖强制检查。未发现测试不算通过。同一问题仅在修正后重试一次，用户/项目指定上限时从其规定。
   - 修复策略遵循 `references/fallback-tdd.md` 3.5 的调试流程

2. **证据优先原则**：
   - 首次验证前读取 `references/verification-evidence.md`，检查前后采集快照，保存真实命令、输出与对应输入
   - 禁止使用"应该通过了"、"看起来没问题"等模糊表述
   - 阶段 5/7 仅按共用证据协议复用结果，无法证明输入与环境一致时重新验证
   - 禁止只跑 lint 就声称"质量检查通过"（lint ≠ typecheck ≠ test）

3. 失败 → 在重试上限内回阶段 3 调试后重验；环境阻塞 → 报告所需条件；三项均不适用 → 报告未验证并明确替代验证方案，不自动进入阶段 5。

4. 满足 `self-check-trinity` 出口（至少一项通过，其余均通过或有依据的不适用）后，以“适用检查通过”进入后续流程：
   - L1 档更新 specs 的 `## Execution State` 节，写入验证命令、证据路径和当前状态。
   - L2 档同步 tracking 状态为“验证通过、待审查”，不提前设置 `delivered`。
   - 随后进入阶段 5（代码审查）。

---

## 阶段 5 内联流程：代码审查

> 本阶段在文档归档前执行，只审查，不提交最终交付、不切换分支、不清理 worktree。L0 聚焦 diff 自审；L1/L2 按复杂度选择自审或已获允许的独立审查，禁止为小任务强制增加子代理。

1. **确定范围**：读取阶段 0 记录的任务基线与既存用户改动，确认实际目标分支；不得默认目标必为 main/master。有目标分支时获取共同祖先；无目标或无提交历史时使用任务开始时的文件基线，不猜测 SHA。
2. **覆盖全部任务改动**：检查已提交差异，以及下列只读命令定位的暂存、未暂存和未跟踪文件；只将本任务内容纳入评审，不修改用户原有改动：

   ```bash
   git diff --no-ext-diff --no-textconv
   git diff --cached --no-ext-diff --no-textconv
   git ls-files --others --exclude-standard
   ```

   未跟踪文件还须读取内容，不能仅看文件名。向审查者提供需求、设计/计划（如有）、全部任务 diff、新文件内容与验证证据；只给两个 SHA 不够。
3. **问题处理**：Critical/Important 修复后，按 `references/verification-evidence.md` 重跑受影响检查并复核修复 diff；Minor 记录影响与取舍。重试服从既有上限，不通过换阶段重置。
4. 阻塞问题为零且证据匹配当前实现后进入正文阶段 6：生成指南、更新索引、完成合规整理与获授权的归档。保留状态快照及归档后路径，完成这些工作后才进入下方阶段 7。

## 阶段 7 内联流程：最终交付与分支集成

### 7.1 最终核对

1. 阶段 6 未完成则先完成文档，不提前处理分支。无文档产出的 L0 直接核对任务结果。
2. 审查阶段 5 后的新增改动，并按 `references/verification-evidence.md` 比较验证输入，执行必要检查；正文与降级路径共享这一协议，不再使用 `git diff HEAD_SHA..HEAD` 去重。
3. 核对本次交付清单包含实现、测试、指南、索引和归档；不能将既存用户改动一并提交。状态快照使用归档后的真实路径，不能重新要求原 plan/tracking 文件存在。

### 7.2 按已有授权交付

| 用户目标 / 已有授权 | 行为 |
| :--- | :--- |
| 仅实现或修复，没有 Git 写操作要求 | 保留工作区，直接汇报实现、验证与限制；不强制询问分支四选一 |
| 已授权本地提交 | 暂存并提交本任务应交付文件；核对暂存树与已验证内容，不自动推送或合并 |
| 已授权推送/PR，目标已明确 | 确认所有应交付文件已纳入提交，再推送并创建/更新 PR，报告真实结果 |
| 已授权合并，目标已明确 | 检查目标分支、工作区与冲突后合并；最终树有变化时验证最终树 |
| 用户要求集成，但目标或该操作授权缺失 | 先完成可审查结果，只询问缺失目标或权限，已有授权不重问 |
| 用户要求放弃开发或删除分支/worktree | 列出影响与待保留改动，取得明确确认后按授权范围处理；禁止清除无关工作 |

- 采用项目约定的实际分支名，不硬编码 `feat/<功能名>`，不为收尾默认 `git pull`。
- 本地提交授权不包含推送、合并、强推或清理工作区权限；批准技术计划也不等于 Git 授权。
- 不自动删除分支或 worktree；已有清理授权仍需确认范围内没有未交付或用户新增的改动。
- 合并/推送后核对交付清单与实际结果一致；若后续又修改验证输入，重新验证并把必要改动纳入交付后才能宣告完成。
